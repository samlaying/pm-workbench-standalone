# 画布重构：ThoughtDAG 思维地图适配方案

## 一、适配结论

可以借鉴 ThoughtDAG，但不建议直接把 PM Workbench 改成通用聊天思维导图。PM Workbench 的核心对象不是“想法”，而是：项目文件、需求、任务、会议结论、项目/人物记忆、Skill 产出和导师审核意见。

因此适配方向应是：

> **以项目为边界、以对话为入口、以 DAG 为上下文组织方式、以文档和任务为最终产出的 PM 工作画布。**

最重要的变化是：连线不再只是视觉关系，而是决定下一次 CLI / Agent 调用能看到哪些节点。

## 二、与现有能力的映射

## 二、产品信息架构：项目、需求点与主题对话

PM Workbench 不应采用“一个项目对应一张无限大总画布”的结构，而应采用三层模型：

```text
项目
  ├─ 需求点 / 开发点 A
  │    ├─ 主题对话：竞品调研
  │    │    └─ 专属画布 A1
  │    ├─ 主题对话：会议纪要
  │    │    └─ 专属画布 A2
  │    └─ 主题对话：需求评审
  │         └─ 专属画布 A3
  └─ 需求点 / 开发点 B
       └─ 主题对话：上线复盘
            └─ 专属画布 B1
```

### 2.1 项目层

项目是最高级边界，包含项目上下文、人物上下文、文件、术语、决策和全部需求点。跨对话引用默认只能发生在同一个项目内。

### 2.2 需求点 / 开发点层

需求点是产品经理真正推进的工作单元，例如“渠道接入调研”“招聘搜索优化”“工作台初始化机制”。它可以包含竞品调研、会议、PRD、评审、汇报、上线复盘等多个主题对话。

### 2.3 主题对话层

每个主题对话只聚焦一件事，例如“整理会议纪要”或“整理竞品调研”。每个对话默认拥有一张独立画布，画布承载这个主题的输入、分析、任务、文档和审核节点。

### 2.4 跨对话引用

用户可以从同一需求点或同一项目下的其他对话引用节点，但引用不是简单复制内容，而是建立带来源的 `reference` 边。被引用节点仍归属于原对话，目标对话只获得摘要、全文或指定片段。

## 三、Agent 主动建立关系

连线不应要求用户手动画。用户可以手动调整，但默认由 Agent 负责识别和维护关系：

1. 创建主题对话时，Agent 判断它属于哪个项目和需求点。
2. 扫描项目文件和历史对话，识别相关的会议、调研、PRD、任务和决策。
3. 为当前对话推荐可引用的其他对话节点。
4. 多 Skill 并行执行后，自动把分析结果连接到输入节点和对应的需求点。
5. 发现同一事实、任务或决策在多个对话中出现时，建立关联或建议合并。
6. 生成主要文档时，自动汇聚相关节点，并记录汇聚依据。
7. 导师审核发现问题时，将意见连接到具体文档、分析节点或来源证据。

Agent 输出的关系操作应结构化、可解释、可撤销：

```json
{
  "graphOperations": [
    {
      "op": "recommend_link",
      "from": "conversation:meeting:node-12",
      "to": "conversation:prd:node-31",
      "kind": "reference",
      "contextMode": "summary",
      "reason": "会议结论直接影响该 PRD 的范围定义",
      "confidence": 0.91
    }
  ]
}
```

涉及自动写入文件、修改记忆、删除节点或覆盖文档时，Agent 只能先提出变更建议，等待用户确认后执行。普通的关联推荐可以自动建立，但必须保留来源和撤销入口。

| ThoughtDAG 概念 | PM Workbench 对应概念 |
|---|---|
| 输入节点 | 用户需求、CLI 命令、项目文件、会议材料 |
| 对话节点 | 某个 Skill 的分析结果或主 Agent 回复 |
| 洞见节点 | 需求判断、风险、决策、候选记忆 |
| 合并节点 | 主 Agent 汇总、PRD、汇报稿、最终结论 |
| 线 | 上下文引用关系、依赖关系、来源关系 |
| 剪枝 | 排除错误、过时或不相关上下文 |
| 分叉 | 从某个需求或结论创建新的分析方向 |
| Frame | 需求点、工作流阶段、评审批次或项目模块 |
| Provenance | 本地文件路径、对话 ID、Skill、消息和版本 |
| Session Atlas | 同项目下多个对话、CLI 执行记录和历史工作记录 |

## 四、PM 画布节点模型

第一版建议只保留以下节点类型，避免一开始做成无限制白板：

- `input`：用户一句话需求或 CLI 命令。
- `file`：项目中的上下文文件、会议材料、PRD、附件。
- `analysis`：某个 Skill 的分析结果。
- `task`：任务拆解、行动项、推进计划。
- `memory`：项目上下文或人物上下文的候选变更。
- `document`：主要文档、PRD、汇报稿、会议纪要。
- `review`：导师审核意见和返工记录。
- `merge`：主 Agent 汇总节点。
- `note`：用户手写的判断或便签。

每个节点必须有：

```json
{
  "id": "node-123",
  "projectId": "project-1",
  "conversationId": "conversation-1",
  "type": "analysis",
  "title": "渠道接入能力分析",
  "content": "...",
  "sourceRefs": ["file:项目上下文.md", "turn:conversation-1:12"],
  "skill": "project-context-maintainer",
  "status": "draft",
  "version": 1,
  "position": {"x": 420, "y": 180},
  "createdAt": "...",
  "updatedAt": "..."
}
```

## 五、连线模型：把线变成上下文

连线至少分为四类：

- `context`：下游 Agent 读取上游节点内容。
- `reference`：只提供摘要或来源链接，节省上下文窗口。
- `depends_on`：表示任务或文档依赖，不一定注入全文。
- `review_of`：表示导师意见针对某个节点或文档版本。

每条线应包含 `from`、`to`、`kind`、`contextMode`、`enabled` 和 `createdBy`。

其中 `contextMode` 可取：

- `full`：注入节点全文。
- `summary`：注入系统摘要。
- `selected`：只注入用户高亮的片段。
- `metadata`：只注入标题、类型、来源和状态。

这样用户可以通过断开一条线，明确告诉 Agent：“这条内容不要再作为当前任务上下文”。

## 六、与 CLI 主入口的结合

CLI 应当是创建和推进思维图的主要入口，Web 画布是审阅和编辑入口。

建议命令：

```bash
pm project scan
pm context show --project current
pm workflow start "整理这个项目的渠道接入方案"
pm workflow status <workflow_id>
pm workflow answer <workflow_id> --option deep
pm graph nodes --conversation current
pm graph connect <source_id> <target_id> --mode full
pm graph disconnect <source_id> <target_id>
pm graph branch <node_id> "只分析技术权限风险"
pm graph merge <node_id> <node_id> --prompt "合并为评审结论"
pm review show <document_id>
pm review revise <review_id>
pm document write <document_id>
```

CLI 的每次执行都应生成可追溯节点，并返回 `workflowId`、`conversationId`、节点 ID 和文件写入结果。Web 端打开同一项目时，读取同一份图数据，而不是依赖浏览器本地状态。

## 七、与多 Skill 并行的结合

### 7.1 明确交付物要在第一步出现

当用户提出“写一份 PRD”“整理成汇报材料”“输出会议纪要”等明确交付目标时，第一轮并行结果不应只是若干分析卡片，而应立即生成一个可编辑的“交付物骨架节点”：

```text
用户需求
  ├─ 项目上下文分析
  ├─ 需求范围与任务拆解
  ├─ 相关历史对话/文件检索
  └─ 交付物模板生成
          ↓
      PRD 骨架 / 汇报骨架 / 会议纪要骨架
```

模板节点先包含目标、背景、范围、用户流程、异常场景、验收标准、风险、待确认项等结构，后续各 Skill 并行填充对应章节。用户可以直接在画布上修改骨架，导师审核也针对这个节点及其章节进行。

### 7.2 记忆更新与交付物并行

项目记忆和人物记忆不是交付完成后的附属动作，而应与文档生成并行：

- 文档 Skill 负责交付物内容。
- `project-context-maintainer` 负责提取项目上下文、决策和术语候选变更。
- 人物记忆分支负责提取角色、负责人、偏好和沟通约束候选变更。
- 主 Agent 负责判断不同 Skill 是否引用了同一事实并消除冲突。
- 记忆候选变更连接到产生它的证据和文档节点。

记忆更新必须区分“候选已识别”和“已确认写入”。只有用户确认后才写入项目文件或人物记忆；但候选节点可以立即出现在画布上，方便用户审阅。

用户一句话进入图后，系统可以生成一个工作流分组：

```text
需求输入
  ├─ project-context-maintainer
  ├─ task-arrangement-planner
  ├─ prd-writer
  └─ meeting-notes-organizer
          ↓
      主 Agent Merge
          ↓
      导师 Review
          ↓
      文档节点 + 任务节点 + 记忆候选节点
```

每个 Skill 节点只接收它上游连入的上下文，避免所有 Skill 默认共享整段历史对话。主 Agent 负责合并、去重、发现冲突；导师节点负责提出返工意见，而不是直接覆盖原始分析。

## 八、必须保留的 PM 特性

ThoughtDAG 的通用能力不能替代 PM Workbench 的约束：

1. 主要文档必须有明确状态：草稿、待审核、需返工、已通过、已写入。
2. 项目记忆和人物记忆只能先生成候选变更，确认后才能写入。
3. 删除节点、断开关键上下文、覆盖文档和写入本地文件要有确认点。
4. 导师意见必须关联具体节点、版本或文档段落。
5. 跨对话引用只能发生在同一项目范围内，且显示来源。
6. 文件节点必须记录路径、文件类型、扫描时间和解析状态。
7. CLI 离线模式也要能查看和编辑图结构，服务恢复后再同步。

## 九、画布交互建议

第一版优先做好以下动作：

- 拖拽节点、框选、多选。
- 从节点创建分支。
- 将多个节点连接到合并节点。
- 点击连线切换全文/摘要/关闭。
- 节点内容预览、就地编辑和引用修改。
- 显示来源文件、Skill、对话和版本。
- 一键“只看当前文档链路”“只看当前任务链路”“隐藏已归档节点”。
- 触控板双指平移、捏合缩放、空格拖动画布，画布滚动不冒泡到页面。

高亮和 PDF 视觉问答等能力放到第二阶段，不应阻塞第一版核心 DAG。

## 十、实施顺序

### Phase 1：图数据层

先新增 `nodes`、`edges`、`frames`、`sourceRefs`、`versions`，并将现有卡片映射为节点。保留旧卡片渲染作为兼容视图。

### Phase 2：上下文编排

让 `/api/message` 根据当前节点和启用连线组装上下文；多 Skill 并行结果分别写入分析节点；主 Agent 写入 merge 节点。

### Phase 3：导师和文档闭环

审核意见写入 review 节点，返工只创建新版本或新分支，不覆盖原始结果；用户确认后写入本地文档。

### Phase 4：CLI / Web 同步

CLI 和 Web 共用图数据 API；CLI 负责发起和推进，Web 负责空间操作和审阅。补齐导出 Markdown、JSON、图片和项目备份。

### Phase 5：高级能力

再考虑高亮强化、PDF 来源溯源、视觉问答、自动凝练、跨工具 Session Atlas 和只读 MCP 查询。

## 十一、第一版验收标准

- 一句话需求可生成输入节点、多个 Skill 分析节点和主 Agent 合并节点。
- 用户可以手动断开一条上下文线，并验证下次分析不再读取该节点全文。
- 同项目不同对话的节点可以引用，但跨项目默认不可见。
- CLI 发起的工作流能在 Web 画布看到，Web 修改的连线能被 CLI 读取。
- 导师审核意见可定位到具体节点和版本，并能触发返工。
- 最终文档、任务、记忆候选都能追溯到来源节点。
- 触控板平移、缩放和页面滚动互不干扰。

## 最终建议

先不要直接接入完整 ThoughtDAG 功能。最有价值、也最符合 PM Workbench 的 MVP 是：

> **项目 → 需求点 → 主题对话 → 专属画布；Agent 主动建立跨对话关系，再通过上下文连线 → 主 Agent Merge → 导师 Review → CLI/Web 共享状态。**

针对本项目，第一版交互改造应优先实现：

1. 创建主题对话时自动归属项目和需求点。
2. 明确交付目标后立即生成可编辑交付物骨架。
3. 多 Skill 并行填充骨架，同时生成项目/人物记忆候选。
4. Agent 自动创建跨对话引用线，并显示“为什么关联”。
5. 用户通过画布查看、编辑、确认和撤销，不负责手动画完整工作流。
6. 保留现有 `/api/message`、工作流等待、并行执行和导师审核逻辑，只替换画布渲染与交互层。

ThoughtDAG 的交互原则可直接借鉴，但在 PM Workbench 中应调整为“Agent 建议和维护关系，人负责确认关键变更”。这既保留自动化价值，也满足项目记忆、人物记忆和正式文档写入的可控性。

这条链路跑通后，再逐步增加分支、剪枝、凝练和 Session Atlas。
