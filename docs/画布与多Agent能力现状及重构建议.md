# 画布与多 Agent 能力现状及重构建议

## 1. 当前产品定位

PM Workbench 是一个面向产品经理的项目工作台：用户绑定一个项目目录后，通过一句自然语言需求触发项目上下文读取、Skill 路由、结构化产出、导师审核，并把主要产出沉淀到对话和项目画布中。

当前画布仍是自研的卡片式画布。Excalidraw 替换方案已经回退，暂不作为当前已实现能力。

## 2. 当前已经具备的能力

### 2.0 CLI 入口（应作为后续主入口）

仓库已经包含 `agent-harness/cli_anything/pm_workbench/` 的 Agent-Native CLI，命令名为 `cli-anything-pm-workbench`。它支持服务模式和离线本地模式，适合后续作为主要工作入口：

- 项目：`project status`、`project bind`、`project scan`。
- 对话：`chat new`、`chat send`、历史读取和清理。
- 画布卡片：`card list`、`card get`、`card add`、`card update`、`card delete`、`card export`。
- 工作流：`workflow status`、`workflow answer`，可承接等待用户确认后的恢复。
- `--json`：为 Agent、脚本和其他自动化流程提供稳定的机器可读输出。
- `--offline`：服务未启动时直接读取/写入本地工作区数据，保证 CLI 基础能力可用。

CLI 与 Web 的关系应定义为“同一工作流的两个入口”，而不是两套功能：CLI 负责高效发起、查看历史、执行和确认；Web 负责画布空间浏览、节点编辑、关系查看和导师意见可视化。

### 2.1 项目与资料

- 左侧项目导航和当前项目切换。
- 关联本地项目文件夹。
- 扫描项目文件并识别基础文件类型。
- 读取项目上下文、内部术语表、项目工作记录、任务、PRD 等核心资料。
- 支持项目级资料挂载到当前对话。
- 支持项目上下文、人物上下文相关入口，但完整增删改查和真实文件同步仍需继续完善。

### 2.2 对话

- 一个项目下可以创建多个对话。
- 对话消息能够触发 Skill 路由。
- 输入框支持使用 `@` 引用画板卡片，并要求 Agent 基于引用内容修改。
- 支持隐藏/显示中间“需求工作台对话推演”区域，隐藏时右侧画布保持显示。
- 对话和画布原则上保持一对一：每个对话拥有自己的画布内容，同时允许跨对话展示和引用。

### 2.3 当前卡片画布

- 将结构化结果生成任务卡片、会议卡片、PRD 卡片、交付模板卡片等。
- 卡片显示来源 Skill 标识。
- 卡片支持预览、就地编辑、引用修改。
- 就地编辑后自动保存。
- 支持关闭/删除画布卡片。
- 支持缩放、放大、缩小和适合视图。
- 支持跨对话画板入口，用于查看或引用同项目其他对话的产出。
- 支持从项目列表点击“画布”聚焦当前项目画布。

### 2.4 多 Skill / 多 Agent 当前实现

当前实现更准确地说是“多 Skill 并行执行”:

1. 服务端根据用户文本、项目文件类型和关键词选择相关 Skill。
2. 多个 Skill 使用 `Promise.all` 并行调用模型。
3. 主 Agent 汇总各 Skill 的文本结果和卡片结果。
4. 汇总结果写入对话，并转成画布卡片。
5. 对项目记忆、人物记忆的候选更新进行提取，并标记为需要确认。

目前已接入的主要 Skill 包括：

- `project-context-maintainer`
- `meeting-notes-organizer`
- `task-arrangement-planner`
- `prd-writer`
- `prd-review-handler`
- `update-writer`
- `meeting-coach`
- `ai-pm-prd-builder`

## 3. 当前工作流机制

### 3.1 用户确认机制

工作流在范围、优先级、交付方式等关键节点先返回问题卡片，状态进入 `awaiting_confirmation`。前端提交答案后，服务端依据原 workflow id 恢复执行，而不是重新开始。

### 3.2 导师审核机制

主 Agent 汇总后进入导师审核。导师检查是否形成主要文档、是否包含目标/范围/验收/异常流程等内容，并返回：

- `approved`：通过。
- `needs_revision`：列出问题，要求返工。

当前返工循环已有基础结构，但审核规则、审核轮次上限、差异对比和用户确认体验还不够完整。

### 3.3 主要文档沉淀

当前主要产出以消息摘要和画布卡片为主。项目文件写入、文档版本、来源追踪、用户确认后的记忆更新还需要进一步统一，避免只在 UI 中生成“看起来像文档”的内容。

## 4. 当前画布的主要问题

1. 卡片布局不是自由画布，内容很多时容易变成长页面，定位和浏览成本高。
2. 缩放、滚动和触控板操作体验不稳定，画布与页面滚动容易互相干扰。
3. 卡片层级、选中状态、拖拽反馈和空间关系不够清晰。
4. 大段 Markdown 直接塞进卡片，信息密度过高，预览与编辑边界不自然。
5. 跨对话引用仍偏“卡片复制/展示”，缺少稳定的引用 ID、来源链和版本关系。
6. Agent 对画布的增删改还不是结构化操作，主要依赖重新生成卡片。
7. 画布与本地文件之间缺少统一的数据模型，难以同时支持任务、文档、记忆、证据和流程节点。
8. 当前已有内容包含历史 mock/演示数据，初始化、清空和真实项目导入边界需要明确。

## 5. 多 Agent 能力的预期

### 5.0 CLI 主入口预期

未来推荐以 CLI 发起完整流程：

```text
pm project scan
  → pm workflow recommend "一句话需求"
  → pm workflow ask / answer
  → pm workflow run --parallel
  → pm review show / approve / revise
  → pm document write
  → pm canvas list / export
```

CLI 需要能够明确显示每个阶段的状态：`scanning`、`awaiting_confirmation`、`running`、`reviewing`、`needs_revision`、`approved`、`written`。每次执行都应返回 `workflowId`、`conversationId`、`projectId`、参与的 Skill、产出文档和画布节点 ID。

CLI 作为主入口时，Web 端必须能实时看到 CLI 创建的对话、文档和画布节点；Web 上的编辑、确认或导师意见也必须能被 CLI 查询和继续执行。所有状态应落在统一的本地项目数据模型中，而不是分别保存在浏览器 LocalStorage 和 CLI 临时状态里。

### 5.1 用户体验预期

用户只说一句话，系统应主动：

1. 扫描当前项目文件和文件类型。
2. 读取最小必要项目上下文。
3. 判断任务类型和涉及的项目/人物。
4. 推荐并行执行的 Skill，并说明各自负责什么。
5. 在需要决策时通过项目内置 ask-user-question 插件暂停并等待回答。
6. 并行执行多个 Skill。
7. 由主 Agent 合并、去重、处理冲突并形成主要文档。
8. 由严格导师审核，提出具体问题。
9. 根据审核意见返工，直到通过或达到轮次上限。
10. 将最终文档写入画布和本地项目文件，并保留来源、版本和确认记录。

### 5.2 能力边界

多 Agent 不应只是多个模型回复拼接，而应具备：

- 明确的 Skill 输入和输出契约。
- 并行任务状态、超时、失败和重试。
- 主 Agent 的去重、冲突处理和最终裁决。
- 导师审核意见与返工任务的对应关系。
- 项目记忆和人物记忆的候选变更审批。
- 所有文件写入的来源和确认记录。

## 6. 画布重构建议

### 第一阶段：先统一数据模型

将画布对象统一为节点，而不是只有卡片：

- `document`：PRD、会议纪要、汇报稿等主要文档。
- `task`：任务、行动项、推进计划。
- `memory`：项目记忆、人物记忆。
- `evidence`：原始文件、消息、引用片段。
- `review`：导师意见和返工记录。
- `group`：同一工作流或同一对话的节点集合。

每个节点至少包含 `id`、`conversationId`、`projectId`、`type`、`title`、`content`、`sourceRefs`、`status`、`version`、`position` 和 `updatedAt`。

### 第二阶段：改成真正的空间画布

- 画布区域独立滚动，页面滚动不再抢事件。
- 触控板双指滚动、捏合缩放、空格拖动画布分别处理。
- 节点拖拽、框选、多选、吸附和自动布局分开设计。
- 长文档使用摘要节点 + 文档详情面板，避免整篇内容堆在画布上。
- 左侧项目栏、中间对话栏、右侧画布栏采用独立可收起布局。

### 第三阶段：接入 Agent 画布操作

让 Agent 输出结构化画布命令，例如：

```json
{
  "operations": [
    {"op": "create", "type": "task", "title": "调研渠道能力"},
    {"op": "update", "id": "node-123", "patch": {"status": "review"}},
    {"op": "link", "from": "node-123", "to": "node-456"}
  ]
}
```

所有修改先进入待应用变更，涉及删除、记忆更新或本地文件写入时必须经过用户确认。

## 7. 推荐的最终工作流

```text
一句话需求
  ↓
CLI / Web 任一入口
  ↓
项目扫描与文件类型识别
  ↓
上下文加载 + Skill 推荐
  ↓
ask-user-question（必要时暂停）
  ↓
多 Skill 并行执行
  ↓
主 Agent 汇总与冲突处理
  ↓
生成主要文档与画布节点
  ↓
导师严格审核
  ├─ 通过 → 用户确认写入本地文件/记忆
  └─ 不通过 → 按意见返工 → 再次审核
```

## 8. 重构验收标准

- 每个对话都有独立画布，并能引用同项目其他对话节点。
- CLI 可以独立完成项目扫描、发起需求、回答问题、查看审核、继续返工和导出文档。
- CLI 与 Web 读取同一份项目、对话、工作流、文档和画布状态。
- 画布节点有稳定 ID、来源、版本和状态。
- 用户可以只使用 CLI/对话，也可以隐藏中间对话而保留画布。
- 一句话能触发多个相关 Skill 并行执行，并能展示执行进度和失败状态。
- 主 Agent 能生成一份主要文档，而不是只拼接多个回复。
- 导师意见能定位到具体节点或文档段落，并驱动返工。
- ask-user-question 能暂停、等待、恢复，且不会重复执行已完成 Skill。
- 文件写入、项目记忆更新和人物记忆更新均有明确确认点。
- 触控板滚动、缩放、拖拽和页面滚动互不抢事件。
- 清空 mock 数据后，初始化项目可以从真实文件重新生成内容。
