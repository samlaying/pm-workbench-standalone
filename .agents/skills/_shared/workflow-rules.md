# Shared Workflow Rules

本文件是工作秘书类 skills 的公共底座。各 skill 只保留自己的任务边界和产出规则；项目识别、上下文获取、结构化确认统一引用这里。

## 结构化确认

当需要用户确认范围、文件名、处理模式、上传目标、取舍方案或缺口信息时，用结构化确认，不绑定单一运行时工具名。

- Claude Code 环境：优先使用 `AskUserQuestion`。
- Codex 环境：优先使用 `request_user_input`；不可用时，用普通消息一次性提出 1-3 个问题。
- 问题要合并，一次问完；能根据上下文合理猜测时，先给推荐选项。
- 未确认前，只能写候选方案或 `【待确认：...】`，不要写成已拍板结论。
- 不在正文里零散追问，不替用户做关键业务决策。

## 项目识别

按证据强度确认项目归属：

1. 输入文件位于包含 `项目上下文.md` 的目录下：直接归属该项目。
2. 输入文件位于项目的 `需求点/` 子目录下：归属该项目和该需求点。
3. 用户明确指定项目名：匹配现有项目目录；有多个近似项目时再确认。
4. 同一批材料涉及多个项目：列出识别结果和证据，用结构化确认让用户选择拆分处理还是指定主项目。
5. 无法从路径或用户描述判断时，只问一个项目归属问题。

目录结构和文件名是主证据；内容只能作为辅助证据，不能覆盖明确的文件路径。

## 上下文获取

确定项目后，默认读取最小上下文：

1. `{项目目录}/项目上下文.md`
2. `{项目目录}/内部术语表.md`（如存在）
3. `{项目目录}/项目工作记录.md`（如存在）
4. `{项目目录}/会议纪要/` 最近 3 条标题
5. 当前需求点的 `01-理解.md`、`10-过程记录.md`（仅在任务命中具体需求点时读取）

读取后直接带入后续处理，不要向用户复述完整上下文。只在发现冲突、缺口或多项目歧义时提出确认。

## 产出验收

每个阶段完成前执行一次二值验收：

- [ ] 目标文件已写入约定目录，文件名和模板结构完整。
- [ ] 所有待确认事项仍保留 `【待确认：...】`，未被写成结论。
- [ ] 本次新增事实、决策和来源已分别写入对应的长期上下文或过程记录。
- [ ] 若阶段要求外部同步，已验证目标文档可打开且内容完整；否则标记为待同步。

## 项目记忆更新

项目记忆由 `project-context-maintainer` 负责定义：

- 长期事实、范围、关键决策、当前卡点：更新 `项目上下文.md`。
- 公司或项目内特殊含义的词：更新 `内部术语表.md`。
- 本次处理过程、来源、阶段性判断：更新 `项目工作记录.md` 或需求点 `10-过程记录.md`。

其他 skill 需要更新项目记忆时，引用本规则，不重复复制完整流程。

## 个人成长分支

`meeting-coach` 属于个人成长/沟通复盘分支，不默认参与项目工作流：

- 不默认读取或维护项目上下文。
- 不提取项目行动项，不写 PRD，不拆任务。
- 只有用户明确要求复盘个人表现、沟通方式、软实力时才触发。
- 同一份会议既要归档又要个人复盘时，先用 `meeting-notes-organizer`，再用 `meeting-coach`。
