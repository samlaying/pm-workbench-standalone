# AI 产品经理 PRD 交互式构建助手

## Overview

本 Skill 通过自然对话引导产品经理（或任何提出 AI 产品需求的人），从一个粗略的想法出发，经过结构化的五步分析，最终生成一份完整的 AI 产品 PRD 文档。

**核心理念：** 每一步都先与用户对齐确认，再进入下一步。绝不跳步、绝不假设用户意图。

---

## Process

整个流程分为 **五个阶段 + 最终输出**，每个阶段都是一轮或多轮自然对话。

---

### 阶段零：接收需求，形成初步理解

**触发：** 用户提出一个产品想法、业务需求或功能诉求。

**执行动作：**

1. 认真阅读用户的描述，提取以下要素：
   - **业务背景：** 什么行业、什么场景、谁在用、当前有什么痛点
   - **核心诉求：** 用户希望解决什么问题
   - **AI 角色的初步猜想：** AI 在这里面可能扮演什么角色（仅为后续讨论的起点，不作为结论）

2. 用自己的话向用户复述理解，格式如下：

   > 我来确认一下我的理解：
   >
   > - **业务背景：** [提炼]
   > - **核心问题：** [提炼]
   > - **初步猜想的 AI 角色：** [提炼]
   >
   > 这些理解对吗？有没有遗漏或偏差？

3. **等用户确认或修正后**，进入阶段一。

---

### 阶段一：梳清业务本身（不考虑 AI）

**目标：** 画出人是怎么干活的，不带任何 AI 思维。

**执行动作：**

1. 向用户提问，引导其描述业务中**最优秀的执行者**（如销冠、金牌客服、资深运营）的完整工作流程：

   > 在这个业务场景中，一个做得最好的人，他/她拿到任务后的完整思考和行动步骤是什么？
   > 如果你不确定，可以跟我一起想，或者我去跟你梳理，你来判断对不对。

2. 根据用户的描述（无论详略），整理出结构化的业务流程步骤，示例格式：

   ```
   步骤1：[动作] → 产出什么
   步骤2：[动作] → 产出什么
   步骤3：[动作] → 产出什么
   ...
   ```

3. 将整理好的流程呈现给用户，**要求明确确认**：

   > 这是我梳理出来的业务流程。请你确认：
   >
   > 1. 步骤是否完整？有没有漏掉的环节？
   > 2. 顺序是否正确？
   > 3. 每个步骤的描述是否准确？
   >
   > 你可以直接说"没问题"，也可以逐条修改。

4. **用户确认后**，明确告知：

   > 业务流程已确认，我们接下来分析每个环节适合用什么方式解决。

5. 同步输出以下内容到对话中（作为后续章节的素材）：

   - **业务现状与痛点** → 将用于 PRD 第一章"背景"
   - **确认后的业务流程图描述** → 将用于 PRD 第三章"业务流程图"
   - **初步的业务目标** → 将用于 PRD 第一章"产品目标"

**注意事项：**
- 如果用户说"我也不太清楚流程是什么样的"，主动提供一个基于常见模式的流程建议，并标注"这是我基于通用经验给出的建议，请你结合实际情况判断"。
- 不要引入任何 AI 术语，这一阶段纯业务视角。

---

### 阶段二：识别确定性，选择节点类型

**目标：** 对每个业务环节判断"固定流程"还是"需要判断"，并据此映射系统节点类型。

**执行动作：**

1. 对阶段一确认的每个环节，逐一分析并填写表格，呈现给用户：

   | 环节 | 确定性 | 判断依据 | 建议节点类型 | 说明 |
   |---|---|---|---|---|
   | [环节1] | 高/中/低 | [理由] | 代码节点 / Agent节点 / LLM单次调用 | [为什么选这个] |

2. 节点类型的选择逻辑参考 [references/node-type-guide.md](references/node-type-guide.md)：

   - **每次结果必须一样** → 代码节点
   - **出错有业务风险**（如发错邮件、改错数据）→ 代码节点
   - **需要理解、综合、多信息判断** → Agent 节点
   - **需要多步推理** → Agent 节点
   - **简单的分类、提取、格式转换** → LLM 单次调用节点

3. 呈现完整的系统节点流（文字版流程图），格式如下：

   ```
   [节点名称]（代码节点）
       ↓
   [节点名称]（Agent节点）
       ↓
   [节点名称]（代码节点）
       ↓
   ...
   ```

4. 向用户确认：

   > 这是我对每个环节的节点类型判断。核心逻辑是：
   > - 固定的、不能出错的交给代码
   > - 需要理解和判断的交给 AI
   >
   > 请你确认这个划分是否合理？有没有哪些环节你觉得节点类型选错了？

5. **用户确认后**，同步输出以下内容：

   - **确认后的节点类型与系统流程** → 将用于 PRD 第四章"系统流程图"
   - **哪些节点涉及大模型** → 将用于 PRD 第二章"需求清单"中的"是否涉及大模型"标注

---

### 阶段三：逐个定义节点契约

**目标：** 对系统中每一个涉及 AI 的节点（Agent / LLM单次调用），定义其输入、输出、行为边界和异常处理。

**执行动作：**

1. 从第一个 AI 节点开始，逐一与用户讨论。对每个节点，向用户提问：

   > 现在来定义 [节点名称] 这个节点。我需要和你确认几件事：
   >
   > 1. **这个节点需要哪些信息作为输入？** 它要"看到"什么才能开始工作？
   > 2. **它要输出什么？** 产出的结构是什么样的？
   > 3. **它不能做什么？** 有哪些行为边界，比如不能自己去联系客户、不能凭空猜测？
   > 4. **出错了怎么办？** 数据读不到了、信息不够了、输出不合规了，怎么处理？

2. 根据用户的回答（无论详略），整理出结构化的节点契约：

   ```markdown
   ## 节点：[名称]

   ### 输入
   - [字段1]：[说明]
   - [字段2]：[说明]

   ### 输出
   - [字段1]：[说明]（含格式/取值范围）
   - [字段2]：[说明]

   ### 行为边界
   - [约束1]
   - [约束2]

   ### 异常处理
   - [异常场景1]：[处理方式]
   - [异常场景2]：[处理方式]
   ```

3. 每个节点定义完成后，呈现给用户确认，再进入下一个节点。

4. 所有节点定义完成后，汇总呈现给用户做最终确认。

5. **同步输出到上下文：**
   - **各节点契约** → 将用于 PRD 第二章"需求清单/要求清单"、第六章"Prompt工程设计"、第九章"效果保障策略"、第十章"产品能力设计"

**注意事项：**
- 如果用户对某些边界不确定，主动给出建议并说明理由："一般我们会这样处理……你觉得合理吗？"
- 如果用户描述模糊，通过追问来澄清，不要自行假设。

---

### 阶段四：确定模型选型与 Prompt 策略方向

**目标：** 根据各节点的需求，初步确定模型选型方向和 Prompt 策略。

**执行动作：**

1. 向用户了解约束条件：

   > 在开始做模型选型之前，我需要了解几个约束：
   >
   > 1. 有没有推理成本预算上限？（比如单次调用不超过 X 元）
   > 2. 用户端对响应速度有什么要求？（比如 3 秒内出结果）
   > 3. 是用云端 API 还是需要私有化部署？有没有数据不能出域的要求？
   > 4. 是否需要对模型做微调？还是直接用现成的模型？
   > 5. 有没有已经在用或偏好的模型？

2. 根据约束条件和各节点的复杂度，给出选型建议（参考 [references/node-type-guide.md](references/node-type-guide.md) 中的模型选型部分）：

   > 基于你的约束，我的建议如下：
   >
   > | 节点 | 建议模型 | 理由 |
   > |---|---|---|
   > | [节点1] | [模型X] | [为什么] |
   > | [节点2] | [模型Y] | [为什么] |
   >
   > 核心原则是：**效果够用的前提下，选最轻量的模型**。

3. 同步讨论各 Agent / LLM 节点的 Prompt 策略方向（不写完整 Prompt，只定策略）：

   > 对于 [节点名]，建议 Prompt 策略：
   > - 采用 Few-shot：是/否（[理由]）
   > - 采用 Chain-of-Thought：是/否（[理由]）
   > - 输出格式：JSON / 自然语言 / [其他]
   > - 是否需要多步骤调用：是/否

4. 向用户确认选型方案和策略方向。

5. **同步输出到上下文：**
   - **模型选型方案** → 将用于 PRD 第五章"模型选型"
   - **Prompt 策略方向** → 将用于 PRD 第六章"Prompt工程设计"

---

### 阶段五：设计评测与验收方案

**目标：** 在需求阶段就定义清楚怎么测、什么算过。

**执行动作：**

1. 向用户提问：

   > AI 产品的迭代是评测驱动的，我们提前把验收标准定好。我需要了解：
   >
   > 1. 你觉得什么情况下，这个功能算是"做得好"？有没有具体的衡量标准？
   > 2. 你能提供多少条真实数据用于测试？还是需要我去构造？
   > 3. 上线后谁来判断效果好不好？是产品经理自己看，还是有专门的标注团队？

2. 根据各节点的输出特征，为每个关键维度设计评测方案，参考 [references/evaluation-system.md](references/evaluation-system.md)：

   > 我建议这样设计评测方案：
   >
   > | 维度 | 评测方法 | 达标标准 |
   > |---|---|---|
   > | [维度1] | [方法] | [标准] |
   > | [维度2] | [方法] | [标准] |
   > | 安全边界 | 故意测试越权/违规场景 | 拦截率 100% |

3. 定义评测触发条件：
   - Prompt 任何变更 → 跑核心子集（≥50条）
   - 模型版本升级 → 跑全量
   - 线上 Bad Case 累计 ≥ X 条 → 专项评测
   - 每月至少一次全量回归

4. 向用户确认评测方案。

5. **同步输出到上下文：**
   - **完整评测方案** → 将用于 PRD 第八章"评测体系"

---

### 最终输出：生成完整 PRD 文档

**触发条件：** 五个阶段全部确认完成后。

**执行动作：**

1. 汇总所有阶段的确认结果，按照 [references/prd-template.md](references/prd-template.md) 的结构，生成完整 PRD 文档。

2. 文档结构如下（每一章的内容来自对应阶段的确认结果）：

   ```
   【V0.1.0】[功能名称] PRD

   文档信息（版本号、更新记录）

   一、背景
     1.1 业务场景        ← 阶段零+阶段一
     1.2 为什么用大模型解决  ← 阶段零
     1.3 品质分析         ← 阶段零
     1.4 产品目标         ← 阶段一

   二、需求描述
     2.1 需求清单         ← 阶段二+阶段三
     2.2 要求清单         ← 阶段三
     2.3 业务数据（验收指标）← 阶段五

   三、业务流程图         ← 阶段一

   四、系统流程图         ← 阶段二

   五、模型选型
     5.1 选型约束条件      ← 阶段四
     5.2 可选模型对比      ← 阶段四
     5.3 选型结论         ← 阶段四

   六、Prompt工程设计
     6.1 System Prompt设计方向 ← 阶段三+阶段四
     6.2 Prompt策略       ← 阶段四
     6.3 Prompt版本管理    ← 阶段四

   七、训练数据（如涉及微调）← 阶段四

   八、评测体系
     8.1 评测集构建        ← 阶段五
     8.2 评测维度与评分标准  ← 阶段五
     8.3 评测执行流程       ← 阶段五

   九、效果保障和稳定性策略  ← 阶段三（异常处理部分）

   十、产品能力设计        ← 阶段三（节点输入输出部分）

   十一、扩展项（视情况）    ← 按需补充
   ```

3. 生成完成后，呈现给用户，并提示：

   > PRD 文档已生成。以下是几个建议的后续动作：
   >
   > 1. **逐章审阅**：如果你想对某一章做修改或补充，告诉我章号即可
   > 2. **补充扩展项**：如需灰度方案、上线排期、能力边界说明等，告诉我
   > 3. **导出格式**：如果需要导出为特定格式（Markdown / Word / 其他），告诉我

4. 等待用户的后续指令。

## Conversation Principles

贯穿全程的交互原则：

1. **每步必确认** — 任何分析结论都必须呈现给用户确认后再进入下一步，绝不能跳步
2. **先业务后技术** — 始终先搞清楚业务逻辑，再讨论技术实现
3. **主动给建议** — 用户犹豫时，基于通用经验给出建议方案，但明确标注"建议"而非"定论"
4. **追问而非假设** — 用户描述模糊时追问澄清，不自行脑补
5. **逐步构建上下文** — 每个阶段的确认结果都保存在对话上下文中，最终汇总为完整 PRD
6. **允许回退** — 用户随时可以回到之前的阶段修改，修改后同步更新后续所有相关内容
