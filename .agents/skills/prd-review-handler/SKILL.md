# PRD 评审反馈处理 Skill

## 触发条件
- 用户说“评审完了，帮我处理反馈”。
- 用户提供评审会录音、妙记、会议转写或评审会纪要，要求按评审意见改 PRD。
- 用户说“拉一下飞书评论”“看最新评论”“对比飞书最新版”。
- 用户给出已评审的飞书 PRD 链接，要求更新本地 PRD。
- 用户说“按评审意见改 PRD”“写验收标准”“把修改回写飞书”。

## 不触发
- 还没有 PRD 初稿或评审稿：改用 `prd-writer`。
- 只整理会议纪要：改用 `meeting-notes-organizer`。
- 只拆任务或推进节奏：改用 `task-arrangement-planner`。

## 工作原则

先读 `../_shared/workflow-rules.md`，按公共规则完成项目识别、上下文获取和结构化确认。

- 飞书是评审后的事实来源之一，但不要盲目覆盖本地文件；先拉最新版和评论，再对比确认。
- 评审会录音/转写、飞书评论、在线编辑差异、用户口头补充必须合并成一张反馈处理清单。
- 每条反馈都要有处理结论：采纳、调整后采纳、不采纳、待确认。
- 评审后修改必须加变更标记，方便二次评审看到变化。
- 验收标准只在流程评审基本确认后编写。
- 所有处理过程写入当前项目或需求点的过程记录，并更新 `项目上下文.md`、`内部术语表.md`、`项目工作记录.md`。

## 项目文件组织

优先根据本地 PRD 所在目录判断项目或需求点：

```text
项目目录/
├── 项目上下文.md
├── 内部术语表.md
├── 项目工作记录.md
└── 需求点/
    └── 需求点名称/
        ├── 10-过程记录.md
        ├── 100-成品.md
        └── 评审/
            ├── YYYY-MM-DD 飞书最新评论.md
            ├── YYYY-MM-DD 飞书最新版本.md
            ├── YYYY-MM-DD 评审会转写.md
            └── YYYY-MM-DD 评审反馈处理.md
```

若项目根或需求点已有其他 PRD 文件名，沿用现有命名。

## 管道总览

```text
飞书 PRD 链接
  -> Phase 0 前置定位
  -> Phase 1 拉最新评论、最新文档和评审会材料
  -> Phase 2 对比与反馈清单
  -> Phase 3 迭代修改
  -> Phase 4 验收标准
  -> Phase 5 版本管理
  -> Phase 6 回写飞书
```

## Phase 0：前置定位

输入：
- 飞书文档链接或 `document_id`。
- 评审会录音、妙记链接、会议转写、会议纪要（可选但常见）。
- 本地 PRD 路径；若用户未给，按项目目录和最近文件推断。

动作：
1. 从飞书链接解析 `document_id`、`wiki_token` 或 `obj_token`。
2. 定位本地 PRD、`项目上下文.md`、`内部术语表.md`、`项目工作记录.md`、需求点 `10-过程记录.md`。
3. 创建或复用 `评审/` 目录，用来存放本次拉取证据和处理记录。
4. 确认本次处理范围：是否处理评审会录音/转写、是否处理评论、是否合并在线编辑、是否写验收标准、是否回写飞书。

暂停点：如果无法确定本地 PRD 或项目归属，先问用户。

## Phase 1：拉最新评论、最新文档和评审会材料

依赖：
- 优先使用飞书 skills：`lark-doc` 读取文档内容，`lark-drive` 管理/读取文档评论，必要时用 `lark-wiki` 解析 wiki 节点。
- 若用户给的是评审会录音、妙记或会议转写，使用 `lark-minutes` / `lark-vc` / 本地转写结果获取会议文字；已给纯文本时直接整理。
- 可直接使用 `lark-cli`；具体子命令以本机 `lark-cli --help` 和对应 skill 说明为准。

动作：
1. 优先运行 `scripts/fetch_lark_review_sources.sh`，它会先检查 `lark-cli` 可用性，再并行拉取飞书文档正文和评论：

```bash
bash <当前 prd-review-handler skill 目录>/scripts/fetch_lark_review_sources.sh \
  --doc "<飞书文档链接或token>" \
  --out-dir "<当前项目或需求点>/评审" \
  --file-type docx
```

脚本输出：
- `评审/YYYY-MM-DD 飞书最新版本.md`
- `评审/YYYY-MM-DD 飞书最新评论.md`
- `评审/YYYY-MM-DD 飞书拉取摘要.md`

2. 若只想检查环境，不拉取内容，运行：

```bash
bash <当前 prd-review-handler skill 目录>/scripts/check_lark_cli.sh
```

3. 若有评审会录音/妙记/转写，提取评审相关内容，保存为 `评审/YYYY-MM-DD 评审会转写.md`。
4. 从评审会材料中抽取：
   - 明确拍板结论
   - 对 PRD 的修改意见
   - 被否掉的方案和原因
   - 仍待确认的问题
   - 后续验收、测试、上线口径
5. 如果脚本失败，再按失败信息检查对应命令；必要时手动执行：

```bash
lark-cli --help | rg -i "comment|docs|drive"
lark-cli docs --help
lark-cli drive --help
```

常用命令形态示例：

```bash
lark-cli docs +fetch --api-version v2 --doc <document_url_or_token> --format pretty
lark-cli drive file.comments list \
  --params '{"file_token":"<file_token>","file_type":"docx"}' \
  --page-all \
  --format json
```

如果本机没有 `drive file.comments list`，使用 `lark-drive` 或 `lark-doc` skill 的评论读取能力完成同等操作，不要跳过评论。

评论表：

| 编号 | 评论位置 | 评论内容 | 评论人 | 评论时间 | 状态 | 分类 |
|------|----------|----------|--------|----------|------|------|
| C-01 | | | | | 未解决/已解决 | 流程修改/补充/删除/疑问/确认/无关 |

评审会反馈表：

| 编号 | 会议位置/时间 | 原话/摘要 | 说话人 | 分类 | 处理建议 |
|------|---------------|-----------|--------|------|----------|
| M-01 | | | | 拍板结论/修改意见/待确认/验收口径/不采纳原因 | |

暂停点：确认已拉到最新评论、最新版和评审会材料；若评论为空，也要明确说明“飞书未拉到未解决评论”。若没有评审会材料，说明本次只基于飞书信息处理。

## Phase 2：对比与反馈清单

输入：
- 本地 PRD。
- `评审/YYYY-MM-DD 飞书最新版本.md`。
- `评审/YYYY-MM-DD 飞书最新评论.md`。
- `评审/YYYY-MM-DD 评审会转写.md`（若有）。

动作：
1. 对比本地 PRD 与飞书最新版：
   - 飞书新增：线上有、本地没有。
   - 飞书修改：两边都有但内容不同。
   - 本地独有：本地有、线上没有。
2. 把评审会反馈、飞书评论和文档差异合并，去重后形成反馈处理清单。
   - 同一条意见在会议和评论中都出现，以会议拍板结论为处理依据，并保留评论编号作证据。
   - 飞书在线编辑和会议结论冲突时，列为待确认，不直接覆盖。
   - 会议中明确“不做/后续再说”的内容，记录为不采纳或后续规划，不写入本期 PRD。
3. 对每条反馈判断影响位置、影响模块、处理建议、待确认问题。
4. 将本阶段结果保存到 `评审/YYYY-MM-DD 评审反馈处理.md`。

差异表：

| 位置 | 本地内容 | 飞书内容 | 差异类型 | 处理建议 |
|------|----------|----------|----------|----------|

反馈处理清单：

| 编号 | 来源 | 内容摘要 | 影响位置 | 处理建议 | 待确认 | 结论 |
|------|------|----------|----------|----------|--------|------|
| F-01 | 会议 M-01 / 评论 C-01 / 差异 D-01 | | | 采纳/调整/不采纳/待确认 | | |

暂停点：逐条确认处理结论。未确认项不得直接写成最终结论。

## Phase 3：迭代修改

动作：
1. 按已确认的反馈处理清单修改本地 PRD。
2. 每处评审后修改加变更标记：

```markdown
[评审反馈-新增] 新增内容
[评审反馈-修改] 修改后的内容
[评审反馈-删除] ~~删除内容~~
```

标记规则：
- 只有评审后的改动加标记；评审前初稿不加“新增”标记。
- 标记放在变更位置行首。
- 删除内容保留并加删除线，便于评审人看到删了什么。
- 同一段落标记超过 3 处时，改为在段落前写一条汇总标记，避免难读。

大范围修改：
- 若超过约 30% 流程被改动，提醒用户建议回到 `prd-writer` 重新确认 Happy Path。
- 用户坚持增量处理时，继续增量修改，但在处理记录中标注风险。

暂停点：确认本地修改是否准确、变更标记是否清楚。

## Phase 4：验收标准

触发：评审反馈已处理，流程基本稳定。

动作：
1. 基于确认后的流程逐模块写验收标准。
2. 验收标准只写“怎么判断完成”，不写实现方式。
3. 使用表格：`编号 | 验收项 | 前置条件 | 操作/触发 | 预期结果 | 备注`。
4. 评论中提到的测试、验收、边界补充优先写入。
5. 涉及用户可见文案的验收项，直接写明预期文案。
6. 缺口径时写 `【待确认：验收口径】`。

规模控制：
- 轻量需求：3-5 条，覆盖核心流程和关键异常。
- 标准需求：10-20 条，按核心流程和异常拆分。
- 完整需求：20+ 条，覆盖模块、权限、数据、异常、边界、文案。

暂停点：逐条确认验收标准，然后合并到 PRD 对应章节。

## Phase 5：版本管理

动作：
1. 将确认后的文档写回本地 PRD。
2. 更新版本记录：
   - 小改：字段、校验、文案、单点规则，版本号 +0.1。
   - 大改：新增流程、模块、重大逻辑变更，版本号 +1.0。
3. 更新 `评审/YYYY-MM-DD 评审反馈处理.md`：
   - 本次是否处理了评审会录音/转写。
   - 评审会提取了多少条反馈。
   - 处理了多少条评论。
   - 采纳/调整/不采纳/待确认分别多少条。
   - 新增/修改/删除了哪些模块。
   - 验收标准是否已写入。
4. 更新 `项目上下文.md` 和 `项目工作记录.md`；需求点场景同步更新 `10-过程记录.md`。
5. 新增内部术语或术语边界变化时，更新 `内部术语表.md`。

暂停点：确认本地版本可以回写飞书。

## Phase 6：回写飞书

依赖：
- `lark-doc`：创建、读取、更新飞书文档内容。
- `lark-drive`：评论读取、评论状态、权限和分享。
- `lark-whiteboard`：图表或白板更新。
- `lark-cli`：可直接执行飞书 API 操作。

动作：
1. 读取 `../prd-writer/references/prd-visual-format.md` 和 `../prd-writer/lark-docx-formatting.md`。
2. 将本地 Markdown 转成飞书 DocxXML。
3. 将变更标记转换为飞书视觉样式：

| 标记 | 飞书样式 |
|------|----------|
| `[评审反馈-新增]` | 绿色高亮/加粗 |
| `[评审反馈-修改]` | 橙色高亮/加粗 |
| `[评审反馈-删除]` | 红色删除线 |

4. 覆盖更新或局部更新飞书文档，按用户确认的方式执行。
5. 图表变化时更新对应白板；失败时保留代码块并记录原因。
6. 对已处理评论执行“标记已解决”；无法自动解决时输出需手动处理的评论清单。

常用命令形态示例：

```bash
lark-cli docs +update --api-version v2 \
  --doc-id <document_id> \
  --action overwrite \
  --content '<DocxXML 内容>'

lark-cli comments +resolve --comment-id <comment_id>
```

输出：

| 同步内容 | 飞书链接 | 变更数 | 评论处理 | 白板处理 | 状态 |
|----------|----------|--------|----------|----------|------|

确认后：将飞书链接、版本号、同步时间写回 `项目上下文.md` 和过程记录。
