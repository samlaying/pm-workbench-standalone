# V2.0 → V3.0 方法论：从"合格"到"一次性通过"

## 目录

- 核心升级：五项能力
- V3.0 自检标准

## 核心升级：五项能力

### 1. 简要背景 + 价值声明
不要从需求背景的历史渊源讲起。开头直接回答三个问题，30 秒内讲完：

| 问题 | 说明 | 示例 |
|------|------|------|
| 为谁做 | 哪个老板/哪个业务方提出的 | "运营团队提出，支持公司新用户翻倍目标" |
| 做完有什么价值 | 对业务、对利益相关方的具体收益 | "注册周期 3天→3分钟，释放运营人力" |
| 不做会怎样 | 简要带一下紧迫性 | "推广期运营手动开通成为卡点" |

**目的：** 让听众在 30 秒内明白"为什么要听我讲这个"。

更详细的数据支撑、竞品对比、战略对齐等维度，在确认背景后按需补充到目标指标或参考章节，不放在开头。

### 2. 整体设计 — 模块化/领域化思维
将功能拆成清晰的业务模块和可复用能力：

**注册能力抽象示例：**
- 不只是"一个注册页面"
- 而是"注册能力"：登录页、视频页、活动页都可能触发
- 说明不同入口的业务边界和跳转结果

**短信能力抽象示例：**
- 不只是"发一条短信"
- 而是"短信通知能力"：注册、登录、改密等场景都可能使用
- PRD 写清楚用户可见结果、失败提示和验收口径；具体路由与服务商实现由研发定义

**写法：**
- 明确说明"本次仅实现xxx，后续可扩展xxx"
- 让研发知道你有全局视野

### 2.5 产品机制骨架 — 目标/状态/触发/完成
在写页面前，先回答“这个功能到底跟什么产品状态发生关系”：

| 维度 | 要回答的问题 | 示例 |
|------|--------------|------|
| 需求结果 | 要改善什么用户行为或业务结果 | 从“不知道如何开始”到“完成首次有效对话” |
| 用户场景 | 用户是谁，刚做完什么，最可能卡在哪里 | 首次激活后进入主对话页，不知道如何使用 |
| 核心状态 | 依赖哪些用户状态、业务对象状态、系统可用状态 | 已激活、未完成引导、有/无在招职位 |
| 触发规则 | 什么时候出现，触发条件是否稳定 | 绑定激活成功，不绑定兑换入口 |
| 完成标准 | 什么算完成/跳过/失败/未完成 | 成功创建职位对话；主动关闭视为跳过 |
| 异常兜底 | 哪些异常会影响体验 | 为空、失败、中断、重复进入、历史用户 |
| 未来扩展 | 入口/角色/对象变化后是否还能承接 | 未来无兑换入口、多 Agent 引导 |

**判断原则：**
- 优先绑定稳定业务状态或产品事件。
- 谨慎绑定页面入口、活动入口、设备缓存、列表为空等不稳定条件。
- 用产品语言表达状态和规则，不写实现方案。

### 3. 表达精准化 — 消除歧义
- 用具体例子说明规则（如"前三位必须是138/182/139"而非"格式正确"）
- 字段名/表名全文使用统一的代码块+颜色标记
- 重要的约束条件用举例+反例同时说明

### 4. 框架性与拓展性 — 搭架子
- 文档结构可被后续产品经理接手和迭代
- **评审后的迭代才加变更标记**，评审前整份文档都是新的，不需要标"新增/修改"
- 迭代时只在变更处加标记，方便评审人快速看到"这次改了什么"

**变更标记写法（评审后迭代时使用）：**
```
[评审反馈-新增] 用户手机号前三位校验规则：增加138/182/139号段校验
[评审反馈-修改] 验证码有效期从5分钟改为3分钟
[评审反馈-删除] 移除"记住密码"功能
```
标记格式：`[评审反馈-新增/修改/删除] 变更内容`，让评审人一眼看到哪些是基于反馈改的。

### 5. 用户体验视角
从"能用"到"好用"：
- 60秒倒计时防重复发送
- Toast 提示（成功/失败/加载中样式）
- 滑块验证防机器人
- Loading 状态、空状态、错误状态
- 注册成功后的引导流

### 6. 目标、验收与业务约束说明（按深度触发）
- 材料中出现”从 X 到 Y””提升/降低/节省/转化率/耗时/成本”等表达时，必须写成正式目标指标
- **验收标准在评审通过后单独写**（Phase 5），不在流程文档中写；评审阶段只确认流程逻辑
- 用户可见文案不能只写模板 ID；涉及短信、邮件、Push、弹窗、Toast、协议时写正文、变量、触发场景和展示位置
- 第三方依赖和风险合并到全局流程总结（3.4）中，不在单独章节写
- 外部服务失败/超时/不可用时，用户看到什么、产品怎么降级或重试
- 数据来源、数据口径、更新频率、权限范围等业务约束
- 涉及合规、风控、支付、通知等关键链路时，说明用户可感知结果和验收标准
- 不写技术实现细节（数据库、系统架构、服务调用等），只写业务级说明

**深度校准：**
- 轻量需求：不单独开”非功能约束”长章节；必要约束并入流程
- 标准需求：涉及用户可见文案、外部依赖或关键异常时补对应小节
- 完整需求：必须写量化目标、关键非功能约束

### 7. 预判评审疑问
写 PRD 时站在评审人视角，提前回答他看到文档后会问的问题：

| 维度 | 示例（用业务语言，不出现技术术语） |
|------|------|
| 数据量级 | "预计日活 5000，高峰期通知可能延迟" |
| 响应时间 | "验证码发出后用户需等待多久，超时怎么提示" |
| 数据来源 | "手机号是否已注册，以账号系统查询结果为准" |
| 重复操作 | "同一用户短时间内重复操作时，展示可理解的限制提示" |
| 历史数据 | "已有 2 万条历史数据，不迁移，新老数据如何共存" |

**为什么重要：** 减少 PRD 评审时的来回沟通成本。

**写法：** 在流程步骤的说明、图表补充或补充说明中，以自然语言嵌入这些约束。若涉及跨系统/第三方协作，可用业务级时序图表达先后顺序。

### 8. 简洁原则
能用简明说清楚的不用一段话，能用表格表达的不用散文：

- 表格 > 散文：结构化信息一律用表格，不要用段落描述
- 简明原则：每个步骤的说明列，单行不超过一个完整的"触发→动作→预期"
- 不重复解释：同一个信息点只在一个位置完整定义，其余位置用"见 X.X"引用
- 删掉修饰词：去掉"的话"、"的情况下"等冗余词，直接写条件和结果

**为什么重要：** 研发和测试在 PRD 中找信息靠搜索和扫读。啰嗦 = 信噪比低 = 关键信息被淹没。

### ⚠️ 不建议做的事
- 不要直接贴代码（受众看不懂、无法维护）
- 不要写技术实现细节（数据库设计、系统架构、服务调用等）
- 不要出现技术术语（接口、API、请求、返回、前端、后端、服务端、状态码等）
- 用业务语言 + 表格 + 按需图表表达产品边界、用户影响和验收口径

## V3.0 自检标准

### 汇报优先
- [ ] 文档顶部有核心摘要块（为谁做、做什么、核心方案、需要谁配合、何时交付）
- [ ] 开头是简要背景（为谁、价值、不做会怎样），不追溯历史渊源
- [ ] 每个模块开头有高亮结论块，详细推导放在后面
- [ ] 非重点内容（数据论证、边界 case、竞品分析、技术细节）标记了"会后查阅"或 read only
- [ ] 结尾有责任分工和交付时间

### 内容质量
- [ ] 流程文档不含验收标准（验收标准在评审通过后单独写，Phase 5）
- [ ] 有整体设计（模块划分、可复用能力、外部依赖/约束）
- [ ] 有产品机制骨架（需求结果、用户场景、核心状态、触发规则、完成标准、异常兜底、未来扩展）
- [ ] 触发规则绑定稳定业务状态或产品事件，没有绑死在临时入口、单个页面、设备缓存或表象推断上
- [ ] 完成标准已区分完成、跳过、失败、未完成
- [ ] 有扩展规划说明
- [ ] 表达无歧义（有具体例子/枚举）
- [ ] 全文无技术术语（接口、API、请求、返回、前端、后端、服务端、状态码等），全部用业务语言
- [ ] 文档结构为"具体流程在前（3.3）、整体总结在后（3.4）"
- [ ] 评审后的迭代已在变更处加 `[评审反馈-新增/修改/删除]` 标记；首次评审前不加标记
- [ ] 交互细节覆盖 Toast/Loading/防重复
- [ ] 信息去重：同一信息点（校验规则、Toast 文案、用户可见文案）只在一个位置完整定义，其余为引用
- [ ] 文档包含必要的业务约束说明（数据量级、响应时间、数据来源、重复操作、历史数据等）
- [ ] 流程图只画分支走向，不包含 Toast 文案和校验规则细节
- [ ] **尽量多放图**：每个页面至少配一个状态流转图或操作流程图；关键判断逻辑用决策树或判断表；跨角色协作用泳道图
- [ ] 已按复杂度选择图表；跨系统/第三方协作场景按需使用业务级时序图
- [ ] 每个字段完整回答必填/样式/校验（三项不允许留空）
- [ ] **每个页面至少覆盖 3 个异常场景**，每条必须回答三个问题：什么情况下发生？用户看到什么？系统怎么处理？
- [ ] 异常从五个角度切入：操作中断、状态变化、时间推移、外部结果、多端/多入口；不写只有分类没有场景的描述
- [ ] 异常场景配有具体的用户可见提示文案
- [ ] 文档无冗余表达，能用简明说清的不用一段话
- [ ] 条件场景已用【第一次】【首次】【非首次】等标记显式区分
- [ ] 默认值已用（默认：xxx）标记
- [ ] 权限/角色差异已用【角色名】标记
