# V1.0 → V2.0 方法论：从"能商量"到"合格"

## 核心升级：四项能力

### 1. 照顾阅读者 — 格式进阶
用统一符号标记文档中的关键元素，让阅读者一眼识别：

| 元素 | 标记方式 | 示例 |
|------|---------|------|
| 按钮 | `【按钮名】` | 【发送验证码】【注册】 |
| 多条件 | `&&` 分隔 | 手机号格式正确 && 手机号未注册 |
| 报错文案 | 斜体 | *请填写正确的手机号* |
| 字段名 | 行内代码 | `phone_number` |
| 引用 | 见用例X.X | 见用例1.3 |

### 2. 逻辑深化 — 按需图表
先判断需求复杂度，再决定需要哪些图表：

| 需求类型 | 推荐图表/产物 |
|---------|--------------|
| 基础版（小 UI 需求） | 关键流程 + 原型/设计稿 + 字段/交互规则 + 验收标准 |
| 中等复杂需求 | 泳道图 / 状态图 / 异常流程 / 权限规则（按需） |
| 大需求、新项目、跨系统需求 | 功能结构图 / 信息架构图 / 业务级时序图 / 高层数据流或业务对象关系图（按需） |

不建议写进 PRD：技术实现细节（数据库、系统架构、服务调用等）。

如果这些内容直接影响产品边界、用户体验、验收口径或合规要求，可以用“业务级说明”写清楚。

### 2.1 业务级时序图（按需）
仅在跨系统、第三方依赖、异步通知、前后台协同时使用，用来表达业务参与方之间的协作顺序：

**参与方划分：**
- 用户（客户端）：前台操作
- 产品系统：承接业务规则和用户状态
- 第三方服务/外部系统：会影响用户结果或验收口径的外部依赖

**时序图要点：**
- 纵向 = 不同参与方
- 横向 = 时间顺序
- 写清楚业务动作、系统响应、外部依赖和结果返回
- 只表达读者需要理解的产品边界和协作顺序
- 不写技术实现细节（数据库、存储、算法、服务拆分等）
- 字段校验、提示文案、权限规则、验收口径引用对应章节，不在时序图里重复定义

### 3. 交互细节 — 字段级说明
为每个输入元素建立完整的交互规格，写在页面/组件说明的"字段"维度行中：

| 列名 | 填写说明 |
|------|---------|
| 字段名 | 中文名称 |
| 必填 | 是/否 |
| 样式 | 文本框/下拉框/单选/多选等 |
| Placeholder | 灰色提示文字 |
| 校验规则 | 格式、长度、范围、关联校验 |
| 校验失败提示 | 用户看到的报错文案 |
| 备注 | 特殊逻辑说明 |

**为什么用表格：** 强制你想到每一个必填项、每一个校验规则、每一个报错文案。表格结构不会让你遗漏。

**硬规则：** 每个字段必须完整回答三个问题——**必填？样式？校验？** 三项不允许留空。如果某字段无需校验，写"无特殊校验"；如果样式待定，写"待设计确认"。不允许出现空白行。

### 4. 数据认知 — 名词解释 + 字段说明
- 先查项目级 `内部术语表.md`，再提取会影响理解和评审的必要术语，统一定义
- 判断标准：新来的实习生只看项目资料，不问任何人，能否理解该词在本公司、本项目里的含义和边界
- 页面名、按钮名、通用交互词、已在字段/流程/交互章节解释清楚的规则，不进入名词解释；公司内部含义特殊的页面/系统/登录叫法除外
- 涉及的表名、字段名用行内代码标记
- 写清楚字段含义、数据来源、有效范围

### 5. 文档引用机制与信息去重
将多处复用的逻辑抽取为独立用例：
- 独立定义一次，其他位置用 `见用例X.X` 引用
- 好处：改一处即全局生效，便于维护

**去重原则（Single Source of Truth）：**
- 一个信息点只在一个位置完整写一次，其余位置用引用
- 校验规则归字段表管，Toast 文案归交互细节表管；技术实现细节不在 PRD 中写，由研发在技术方案中定义
- 流程步骤只写"骨架"（触发条件→执行动作→走向），细节指向对应章节

## V2.0 自检标准
- [ ] 所有按钮用【】标记
- [ ] 多条件用&&分隔
- [ ] 已按复杂度选择图表；跨系统/第三方/异步协作场景按需使用业务级时序图
- [ ] 有字段级交互表格
- [ ] 必要术语已解释；无必要术语时不强行凑名词解释
- [ ] 字段名/表名用行内代码标记
- [ ] 复用逻辑已抽取并建立引用关系
- [ ] 同一信息点未在多处完整重复定义（校验规则、Toast 文案、用户可见文案各只出现一次；全文无技术术语）
