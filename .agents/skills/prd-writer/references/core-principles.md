# PRD 写作核心原则

## 汇报优先

PRD 既是汇报材料也是会后参考文档，但汇报体验优先于文档完整性。

1. 文档最顶部放摘要块，简要写明做什么、核心方案、需要谁配合、何时交付。
2. 背景只回答“为谁做、做完有什么价值、不做会怎样”，30 秒内讲完。
3. 每个模块开头用高亮块写核心结论，详细推导、数据、边界 case 放后面。
4. 必讲内容现场讲；补充细节标注“以下为补充细节，会后查阅”。
5. 结尾明确分工：谁负责什么、需要谁协助、各自什么时候交付。

## 评审走查材料落位

当用户提供“评审讲解”“逐页讲解”“用户看到什么、做什么、然后看到什么”这类材料时，必须拆进 PRD 的五个位置：

| 材料类型 | 融入位置 | 写法 |
|----------|----------|------|
| 正常流程页 | `页面/组件说明` | 按“用户看到什么 -> 用户能做什么 -> 然后发生什么”写 |
| 异常状态 | 页面异常行 + 全局风险表 | 写清触发条件、提示、下一步可操作项、待确认策略 |
| 已有页面新增入口 | `页面/组件说明` | 明确“已有页面改造，不是新页面”；说明展示条件、禁用态、跳转目标、是否可独立排期 |
| 待讨论问题 | `待确认项` 或页面块的 `评审待确认` 行 | 给 2-3 个可选方案，不只写“需确认” |
| 现场讲解顺序和预计时间 | `评审讲解提纲` | 放在 PRD 末尾，标记为评审现场使用，不替代正文 |

每个页面/组件的评审口径固定回答三句话：

1. 用户看到什么：页面、弹窗、列表、提示长什么样，关键文案是什么。
2. 用户能做什么：可点击、可选择、可跳过、可重试、可进入哪里。
3. 然后发生什么：自动关闭、跳转、列表新增、进入详情、保留原页面等。

## 难缠用户兜底

把用户默认想象成：脾气最大、智商最低、最没耐心、最小气的人。

红线：
- 不假设用户会猜、会等、会自救。
- 每个功能必须讲清存在理由。
- 任何设计不得偏离难缠用户和功能定位。

硬性要求：
- 关键按钮点击后 1 秒内有反馈。
- 成功有明确结果，失败有原因和补救。
- 表单、选择、编辑失败后默认保留内容。
- 空态、无结果、到底、不可点、无权限、过期、部分成功都要提示。
- 高风险操作必须二次确认或可撤销。
- 不让用户做系统可代劳的事。
- 文案零歧义。

每个模块开头强制写：

```markdown
**功能定位：** 让【目标用户】能【完成什么事】。
**违背这句话的设计，不做。**
```

## 产品机制设计

写 PRD 时，不要从“页面放什么、弹窗几步、按钮叫什么”开始。先回答：

- 这个需求要改变什么用户行为？
- 用户在哪个状态下需要它？
- 系统在什么状态下才应该触发它？
- 什么算完成？
- 哪些异常会影响用户体验？
- 未来入口变了，这个设计还站不站得住？

初级表达是“做一个功能、加一个页面、弹一个引导、放几个按钮”。成熟表达是“在某类用户处于某个业务状态、系统处于某个可用状态时，通过某个机制帮助用户完成某个目标结果”。

详细方法见 `product-mechanism-design.md`。

## 产品边界

产品必须想：
- 用户关闭、跳过、中断后，下次是否还出现。
- 前置流程失败时，用户看到什么，是否能继续。
- 空数据时用户怎么开始，是否被卡死。
- 数据加载失败时，是否会误判成空态。
- 未来入口变化后，机制是否还成立。
- 用户完成过同一机制后，换设备、换入口、隔很久回来是否还触发。

产品不要写：
- 使用 localStorage、cookie 还是数据库字段。
- 接口超时几秒。
- 并发请求怎么加锁。
- 重试机制怎么编码实现。
- 具体代码、表结构、状态码。
