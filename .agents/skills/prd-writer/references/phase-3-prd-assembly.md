# Phase 3：结构化 PRD

## 目标

使用 `templates/prd-v3-template.md` 输出评审前 PRD。

## 章节结构

1. 核心摘要：文档最顶部放摘要块，直接写清“为谁做、做什么、核心方案、需要谁配合、何时交付”。
2. 简要背景：只回答三个问题：为谁做、做完有什么价值、不做会怎样。
3. 名词解释：使用 `内部术语表.md` 中已确认定义；无必要术语可写“无”。
4. 页面/组件说明：先写 `3.1 产品机制骨架`，再在 `3.2 页面/组件明细` 按页面表格组织具体流程。
5. 全局流程总结：结论前置，再展开数据依赖、全局规则、外部依赖与风险、流程图。人员依赖和详细流程标记为 read only。
6. 产品机制设计：写清结果、用户、状态、触发、完成、兜底。
7. 待确认项：按页面、问题、推荐方案、影响范围组织。
8. 非功能约束：仅在影响体验、验收、合规或风险时写。
9. 责任分工与交付时间：谁负责什么、需要谁协助、各自什么时候交付。
10. 评审讲解提纲：围绕“用户看到什么、能做什么、然后发生什么”讲。
11. 参考/对标：标记为 read only，按材料情况写。

## 图表原则

- 能用图说清楚就放图，优先业务流程图、泳道图、状态图、信息架构图。
- 不画实现级架构图、数据库图、接口调用图。
- 图表和飞书白板规则参考 `prd-visual-format.md`。

## 输出前自检

- 是否没有技术实现术语。
- 是否每个功能模块、页面、核心流程都有不超过 25 字的功能定位。
- 是否每个新增设计都能解释为服务功能定位，不能解释的已砍掉或放入“不做/待确认”。
- 用户点关键按钮后，1 秒内是否有状态变化。
- 操作成功时，用户是否明确知道成功了。
- 操作失败时，用户是否知道失败原因和补救方式。
- 表单/编辑/选择流程失败或中断后，用户已填写内容是否保留；若不保留是否有提示。
- 空态、无结果、到底、不可点、无权限、过期、部分成功是否都有用户可见提示。
- 删除、覆盖、提交后不可改等高风险操作是否有二次确认或撤销策略。
- 是否每个页面都有具体异常，而不是抽象异常分类。
- 是否用户可见文案写了正文。
- 是否一个信息点只在一个权威位置完整定义。
- 是否过程信息没有写进最终 PRD。
- 是否文档顶部有核心摘要块。
- 是否每个模块开头有高亮结论块。
- 是否每个页面都能用“用户看到什么、能做什么、然后发生什么”讲清楚。
- 是否把评审讲解材料拆进了页面/异常/待确认/讲解提纲，而不是整段堆在一个章节。
- 是否把已有页面新增入口写成独立改造点，并说明是否需要改版、能否独立排期。
- 是否把需求从功能描述升级为产品机制设计。
- 是否避免用不稳定条件做关键判断，如临时入口、浏览器缓存、加载失败后的空态假象。
- 是否非重点内容标记了“会后查阅”或 read only。
- 是否结尾有责任分工和交付时间。

质量参考：`v2-to-v3.md`、`quality-checklist.md`、`single-source.md`。

暂停点：必须通过结构化确认来确认评审前 PRD 是否可提交。确认后写入 `100-成品.md` 或沿用现有 PRD 文件；未确认前不得当作最终评审稿。
