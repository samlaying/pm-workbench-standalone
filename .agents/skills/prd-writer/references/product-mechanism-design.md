# 产品机制骨架：从功能描述到机制设计

## 目标

把需求从“做一个页面/弹窗/按钮”提升成“某类用户在某种状态下完成某个目标，并把产品状态推进到下一步”。

这套方法适用于大中小需求：
- 小需求：用它防止漏掉触发、完成和关键异常。
- 中需求：用它支撑 PRD 的整体设计和异常场景。
- 大需求：用它搭出模块、状态、版本和扩展结构。

## 六问法

| 问题 | 要回答什么 | 常见产出 |
|------|------------|----------|
| 结果 | 这个需求要改善什么用户行为或业务结果 | 从什么状态到什么状态、目标指标 |
| 用户 | 谁在什么场景、什么心态下遇到它 | 用户角色、进入前动作、核心卡点 |
| 状态 | 需求依赖哪些状态 | 用户状态、业务对象状态、系统可用状态 |
| 触发 | 什么时候出现，条件是否可靠 | 稳定业务事件、触发条件、排除条件 |
| 完成 | 什么叫完成，什么叫跳过/失败/未完成 | 完成标准、状态流转、后续是否再出现 |
| 兜底与扩展 | 哪些异常影响体验，未来变化能否承接 | 异常矩阵、扩展点、本期不做 |

## 状态判断原则

优先绑定稳定状态，不绑定临时入口。

| 判断对象 | 稳定性 | 示例 | 风险 |
|----------|--------|------|------|
| 业务状态 | 高 | 已激活、已完成引导、有在招职位 | 推荐优先使用 |
| 产品事件 | 高 | 激活成功、首次有效对话创建成功 | 推荐优先使用 |
| 用户行为 | 中 | 点击开始、选择职位、关闭弹窗 | 适合定义完成/跳过 |
| 页面入口 | 低 | 兑换页、活动页、某个落地页 | 未来入口变化会返工 |
| 设备状态 | 低 | 浏览器缓存、本地记录 | 清缓存、换设备会失真 |
| 表象推断 | 低 | 对话列表为空、数据加载为空 | 容易把失败/归档误判成真实状态 |

写 PRD 时用产品语言表达：
- 推荐：以用户账号维度记录是否完成引导。
- 推荐：以 Agent 激活成功作为可用标志。
- 避免：存服务端/前端缓存/接口返回/数据库字段。

## 规模裁剪

### 轻量需求

只写 4 行：

| 维度 | 写法 |
|------|------|
| 需求结果 | 希望用户/业务从 A 到 B |
| 核心状态 | 依赖的 1-2 个关键状态 |
| 触发与完成 | 什么时候出现，什么叫结束 |
| 关键异常 | 最可能影响体验的 1-3 个场景 |

### 标准需求

写完整骨架：

| 维度 | 结论 | 待确认 |
|------|------|--------|
| 需求结果 | | |
| 用户场景 | | |
| 核心状态 | | |
| 触发规则 | | |
| 完成标准 | | |
| 异常兜底 | | |
| 未来扩展 | | |

### 完整需求

在标准骨架上增加：
- 核心对象状态表。
- 状态流转图。
- 多角色/多入口差异。
- 本期范围与后续扩展边界。
- 版本策略：不同版本的引导、规则或配置是否需要共存。

## PRD 落位

产品机制骨架放在页面/组件说明开头，作为读者理解页面流程的前置逻辑。

不要把它写成长篇理念说明。每个格子尽量 1-3 条要点。

## 自检

- [ ] 是否说清楚“这个需求要改变什么结果”。
- [ ] 是否先定义状态，再写页面。
- [ ] 触发条件是否绑定在稳定业务状态或产品事件上。
- [ ] 是否定义了完成、跳过、失败、未完成。
- [ ] 异常是否从用户体验出发，而不是从技术分类出发。
- [ ] 未来入口、角色、对象变化后，设计是否还能承接。
- [ ] 文档没有出现实现级技术术语。
