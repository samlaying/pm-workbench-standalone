# Phase 0.5：产品机制骨架

## 目标

在写页面前，先把需求从“做一个功能”提升成“设计一个稳定的产品机制”。本阶段用于大中小需求，按规模控制深度。

## 核心问题

1. 结果：这个需求要改善什么用户行为或业务结果？
2. 用户：谁在什么场景、什么心态下遇到它？
3. 状态：它依赖哪些用户状态、业务对象状态、系统可用状态？
4. 触发：什么时候出现？触发条件是否稳定，未来入口变化后是否仍成立？
5. 完成：什么叫完成？什么情况算跳过、失败、未完成？
6. 兜底与扩展：哪些异常会影响体验？未来入口、对象、角色、版本变化后是否还能承接？

## 规模控制

| 需求规模 | 必写骨架 | 不写/少写 |
|----------|----------|-----------|
| 轻量 | 简要目标、核心状态、触发与完成、关键异常 1-3 条 | 长篇模块设计、复杂状态图 |
| 标准 | 目标、用户场景、状态表、触发/完成规则、异常入口、扩展判断 | 实现级方案 |
| 完整 | 完整机制骨架、对象状态流转、关键业务事件、版本/多角色/多入口扩展 | 技术架构、数据库、代码 |

## 写法要求

- 用业务语言表达，不写技术实现术语。
- 功能定位不超过 25 个字，格式为“让【目标用户】能【完成什么事】”。
- 触发规则优先绑定稳定的业务状态或产品事件，不绑定临时入口、单个页面、浏览器缓存等不稳定条件。
- 完成标准必须能指导后续异常场景和评审后验收标准。
- 最难缠用户兜底必须覆盖：即时反馈、成功提示、失败补救、空态/到底、内容保留、不可逆操作。
- 背离判断必须列出“本期不做”的贪心扩展，避免把一个清晰功能做成另一个产品。

## 询问方式

- 凡需要询问用户或让用户确认，必须使用结构化确认；不要在正文里直接问，也不要替用户拍板。
- 每个维度单独确认，不要合并。
- 每次提问时，先基于材料给出初步判断，再列出 2-3 个不同角度的产品判断让用户选择。
- 选项要启发思考，不是简单“对/错”，而是从不同产品视角切入。
- 用户确认一个维度后，再问下一个。全部确认后再进入 Happy Path。

详细方法参考 `product-mechanism-design.md`。
