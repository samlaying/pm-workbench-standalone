## 一、汇报优先（核心结构）

> PRD 既是汇报材料也是会后参考文档，汇报体验优先于文档完整性。

- [ ] 文档顶部有核心摘要块：为谁做、做什么、核心方案、需要谁配合、何时交付
- [ ] 核心摘要中有功能定位：`让【目标用户】能【完成什么事】`，不超过 25 个字
- [ ] 开头是简要背景：只回答"为谁、价值、不做会怎样"，30 秒内讲完，不追溯历史渊源
- [ ] 每个模块（产品机制骨架、页面明细、全局流程总结）开头有高亮结论块
- [ ] 非重点内容（数据论证、边界 case、竞品分析、人员依赖、详细流程图、参考对标）标记为 read only 或"会后查阅"
- [ ] 结尾有责任分工与交付时间表（角色、负责人、职责、交付物、交付时间）

## 一点五、伺候难缠用户红线

- [ ] 每个功能模块、页面、核心流程都有功能定位，且能作为争议时的裁判标准
- [ ] 所有新增入口、字段、弹窗、流程分支都能解释为服务功能定位；不能解释的已删除或列入本期不做
- [ ] 用户点关键按钮后 1 秒内有可感知状态变化（Loading、禁用态、进度、Toast、页面变化至少一种）
- [ ] 操作成功有明确成功提示或结果变化，不依赖研发/运营“知道成功了”
- [ ] 操作失败写清失败原因、用户可补救动作、是否可重试
- [ ] 表单、选择、编辑类流程失败或中断后，已填写内容默认保留；不保留时写清提示和补救路径
- [ ] 空态、搜索无结果、列表到底、不可点、无权限、已过期、部分成功都有用户可见提示
- [ ] 删除、覆盖、提交后不可改等高风险操作有二次确认或可撤销策略；不做时列入待确认并说明风险
- [ ] 不要求用户做系统可以代劳的事；必须让用户选择时，给默认推荐或清楚说明差异
- [ ] 用户可见文案零歧义：用户不需要知道内部规则，也能判断点完会发生什么

## 二、规模与深度校准
- [ ] 已判断需求规模（小需求/大需求）和交付深度（轻量/标准/完整），并记录判定理由
- [ ] 轻量需求没有被写成完整项目方案；只保留背景、关键流程、字段/交互规则、验收标准和必要异常
- [ ] 标准需求包含验收标准；涉及用户可见文案、外部依赖或关键异常时已补对应小节
- [ ] 完整需求包含量化目标、验收标准、关键非功能约束、外部依赖、风险与降级、按需图表
- [ ] 缺失信息只在影响范围、排期、验收或风险等级时追问；其他合理假设已标注 `【待确认】`

## 三、逻辑完整性
- [ ] 已先完成产品机制骨架：需求结果、用户场景、核心状态、触发规则、完成标准、异常兜底、未来扩展
- [ ] 触发规则绑定稳定业务状态或产品事件，没有绑死在临时入口、单个页面、设备缓存或表象推断上
- [ ] 完成标准已区分完成、跳过、失败、未完成，能支撑异常场景和评审后验收标准
- [ ] 每个流程节点都有 条件→动作→预期
- [ ] 每个判断节点都有 Yes 和 No 分支
- [ ] 异常流程全部覆盖，无遗漏
- [ ] Phase 2 异常候选已通过结构化确认逐批与用户确认（每批 3 个，是否覆盖、触发条件、系统行为、用户提示）
- [ ] 所有"跳转到哪里"都有明确目的地
- [ ] 同一手机号多次发送验证码的逻辑已说明
- [ ] 已注册手机号的处理方式已说明
- [ ] 页面/组件说明已使用表格输出（列：页面/组件 | 原型图 | 维度 | 详细说明）
- [ ] 每个页面都能映射到所属模块

## 四、交互完整性
- [ ] 所有输入字段都有校验规则和报错文案
- [ ] 必填项已标注
- [ ] 按钮状态变化已说明（置灰/可点击/Loading），且关键按钮点击后 1 秒内有反馈
- [ ] 防重复点击机制已说明
- [ ] Toast 提示（成功/失败/通用错误）已说明
- [ ] 页面加载状态已说明
- [ ] 只有一个"确定"按钮的弹窗已写清点击后果；涉及破坏性结果时不用单按钮确认

## 五、格式规范
- [ ] 按钮统一用【】标记
- [ ] 多条件用 && 分隔
- [ ] 字段名/表名用行内代码标记
- [ ] Markdown 标题层级正确（不跳级）
- [ ] 最终 PRD 不包含"提取与确认记录""业务信息提取""反问确认结论""文档版本历史"等过程性章节
- [ ] 文档间引用关系标注清晰（一般不需要单独的引用关系表）

## 六、图表与异常覆盖
- [ ] **尽量多放图**：每个页面至少配一个状态流转图或操作流程图
- [ ] 关键判断逻辑用决策树或判断表
- [ ] 跨角色协作用泳道图，多状态用状态图
- [ ] 小 UI 需求至少包含关键流程图、原型/设计稿、字段/交互规则
- [ ] 中等复杂需求按需补充泳道图、状态图、信息架构图
- [ ] 大需求/新项目/跨系统需求按需补充功能结构图、业务级时序图、高层数据流或业务对象关系图
- [ ] **每个页面至少覆盖 3 个异常场景**，每条必须回答三个问题：什么情况下发生？用户看到什么？系统怎么处理？
- [ ] 异常从五个角度切入：操作中断、状态变化、时间推移、外部结果、多端/多入口
- [ ] 不写"网络异常→提示错误"这种只有分类没有场景的描述
- [ ] 异常场景配有具体的用户可见提示文案
- [ ] 第三方服务依赖已列出（只写产品边界、用户影响和验收口径）

## 七、评审与验收流程
- [ ] 流程文档（不含验收标准）已提交评审，评审反馈已逐条处理
- [ ] 评审通过后才编写验收标准，未在流程未确认时提前写入
- [ ] 验收标准基于评审确认的流程编写，覆盖核心流程、异常场景、权限/数据/文案
- [ ] 验收标准已按需求规模控制条数（轻量 3-5 条、标准 10-20 条、完整 20+ 条）

## 八、目标、验收与约束
- [ ] 材料中出现"从 X 到 Y""提升/降低/节省/转化率/耗时/成本"等表达时，已写成正式目标指标
- [ ] 没有量化口径时未硬编数据，已标注 `【待确认：量化口径】`
- [ ] 涉及短信、邮件、Push、站内信、弹窗、Toast、协议等用户可见文本时，已写正文、变量、触发场景和展示位置
- [ ] 非功能约束只在影响用户体验、验收、合规或风险时出现，且写业务级约束而非实现方案
- [ ] 外部依赖和风险已合并到全局流程总结中，只写产品边界、失败影响、用户可感知表现、降级方式和验收口径

## 九、可维护性
- [ ] 复用逻辑已抽取为独立用例
- [ ] 评审后的迭代已在变更处加 `[评审反馈-新增/修改/删除]` 标记；首次评审前不加标记
- [ ] 已先读取并维护项目级 `内部术语表.md`
- [ ] 名词解释符合"新实习生不问人也能看懂"的标准
- [ ] 名词解释只保留必要术语：项目特殊含义、缩写/内部代号、公司内特殊叫法、跨系统身份/状态、影响权限/流程/权益/数据口径的概念
- [ ] 名词解释未收录纯页面名、按钮名、通用交互词等上下文已自解释内容；公司内部含义特殊的页面/系统/登录叫法除外
- [ ] 当前版本文档已回写（需求文档-当前版本.md）
- [ ] 变更日志已更新
- [ ] 存在模块影响矩阵（模块/变更类型/影响范围）
- [ ] 每个模块有原型图/页面引用（链接或锚点）

## 十、信息去重（Single Source of Truth）
- [ ] 校验规则只在页面说明（字段维度）完整定义，全局流程总结中用"规则见 X.X"引用
- [ ] Toast/提示文案只在页面说明（交互维度）完整定义，全局流程总结中用"提示见 X.X"引用
- [ ] 文档不含技术实现细节（数据库、系统架构、服务调用等）
- [ ] 全文无技术术语（接口、API、请求、返回、前端、后端、服务端、状态码等）
- [ ] 业务级时序图只在跨系统/第三方协作场景按需出现，且不重复定义流程、字段、提示和权限规则
- [ ] 同一信息点搜索后出现不超过 1 次完整定义（其余均为引用）

## 十一、背景与价值
- [ ] 需求背景有具体数据支撑
- [ ] 价值描述可量化
- [ ] 与公司目标/战略有关联说明
- [ ] 功能清单状态已更新

## 十二、提取与确认闭环
- [ ] 已从录音/文档提取项目背景、项目预期、变更模块
- [ ] 关键提取结果有来源证据（录音片段/文档位置）
- [ ] 凡涉及询问用户、让用户确认、选择方案、拍板范围或补充缺口，均已使用结构化确认
- [ ] 已通过结构化确认来确认关键问题，不依赖用户自行阅读待确认清单后统一确认
- [ ] 未确认项已明确标注风险，不混入已确认结论
- [ ] 已完成"小需求/大需求"判定，并通过结构化确认和用户确认判定结果
- [ ] 若为小需求，第一部分（需求背景）已精简，且总篇幅未超过完整版约2/3

## 十三、预判与简洁
- [ ] 文档包含评审人会关注的业务约束（数据量级、响应时间、数据来源、重复操作、历史数据处理）
- [ ] 流程图只画分支走向，Toast 文案和校验规则细节在文字说明/字段表中
- [ ] 若使用业务级时序图，只表达业务动作、系统响应、外部依赖和结果返回的先后顺序
- [ ] 每个字段完整回答必填/样式/校验（三项不允许留空）
- [ ] 能用简明说清的不用一段话，能用表格的不用散文
- [ ] 定位模糊的模块已拆分或砍范围，没有把聊天做成社区、把搜索做成内容中心这类定位背离
- [ ] 同一信息点搜索后出现不超过 1 次完整定义（其余均为引用）
