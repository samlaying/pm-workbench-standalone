# Single Source of Truth（单一事实来源）

## 核心原则

> **一个信息点，只在一个权威位置完整定义一次；其余位置如有需要，只用"引用"而非"复述"。**

## 一、章节职责划分

每个章节有它天然擅长承载的信息类型，不得越界重复定义：

| 章节 | 管辖范围 | 允许写什么 | 不允许写什么 |
|------|---------|-----------|-------------|
| 产品机制骨架（页面/组件说明开头） | 需求的判断依据 | 需求结果、用户场景、核心状态、触发规则、完成标准、关键异常、未来扩展 | 页面细节、字段规则、完整提示文案、实现方案 |
| 页面/组件说明（第三章） | 页面级详细说明 | 触发条件、核心流程、异常、系统逻辑、信息架构、字段、交互、文案、边界、权限 | 技术实现细节 |
| 全局流程总结（第四章） | 动作顺序、分支走向、依赖、风险 | 触发条件 → 执行动作 → 成功/失败走向、外部依赖、风险与降级 | 校验规则细节、Toast 完整文案 |
| 验收标准（第五章，评审通过后写） | 完成判断 | 前置条件、操作/触发、预期结果 | 实现方案 |
| 非功能约束（第六章，模型判断） | 影响体验/验收/合规/风险的业务级约束 | 响应时间、频控、可用性、数据口径、权限范围 | 技术实现方案 |

## 二、引用格式规范

需要指向别处时，用明确锚点，不重新写一遍：

**错误（复述）：**
> 步骤2：系统校验手机号格式（11位纯数字，首位为1，前三位匹配运营商号段13x/14x/15x/16x/17x/18x/19x），格式错误→Toast"请填写正确的手机号"

**正确（引用）：**
> 步骤2：系统校验手机号格式（规则见 3.3），校验失败→提示见 3.3「手机号格式错误」

引用格式统一使用：`见 X.X 章节名 — 具体条目`

## 三、常见重复模式与修正

| 重复模式 | 出现位置 | 修正方式 |
|---------|---------|---------|
| 校验规则同时写在全局流程总结和页面说明 | 3.4 + 3.3 | 全局流程总结中改为"规则见 3.3 页面说明" |
| Toast 文案同时写在全局流程总结和页面说明 | 3.4 + 3.3 | 全局流程总结中改为"提示见 3.3「场景名」" |
| 用户可见文案只写模板 ID | 3.3 文案维度 | 补正文、变量、触发场景、展示位置；模板 ID 只是辅助信息 |
| 验收标准写成实现方案 | 5 | 改为前置条件、操作/触发、预期结果 |
| 同一逻辑在流程和时序图都完整描述 | 3.4 + 3.7 | 流程写用户路径和业务规则，时序图只补充跨系统/第三方协作关系，不重叠 |
| 技术实现细节写在 PRD 中 | 不应出现 | 技术方案由研发定义，PRD 只写业务级说明 |
| 异常场景同时在全局流程总结和页面说明出现 | 3.4 + 3.3 | 全局流程总结只写走向，页面说明是提示文案的唯一定义处 |

## 三.5、图与文字的分工

流程图和文字说明各司其职，不互相替代：

| 载体 | 画什么 | 不画什么 |
|------|--------|---------|
| 流程图（Mermaid flowchart） | 分支走向、判断节点、动作步骤 | Toast 文案、校验规则细节、字段定义 |
| 页面/组件说明（3.3） | 触发条件→核心流程→异常→系统逻辑→字段→交互→文案→边界→权限 | — |
| 业务级时序图（按需） | 跨系统/第三方协作顺序、用户可感知结果 | 技术实现细节 |

**原则：** 流程图是"地图"——只画路线和路口；文字说明是"导航"——告诉你在每个路口怎么做。

**尽量多放图：** 每个页面至少配一个状态流转图或操作流程图；关键判断逻辑用决策树或判断表；跨角色协作用泳道图。

## 四、信息注册表模板

每个信息点只注册一次，明确"家"在哪里：

| 信息点 | 唯一定义位置 | 引用位置（不重复定义） |
|--------|------------|---------------------|
| 手机号校验规则 | 3.3 页面说明-字段维度 | 3.4 全局流程总结 |
| Toast 文案（所有） | 3.3 页面说明-交互维度 | 3.4 全局流程总结 |
| 验证码发送结果口径 | 5 验收标准（评审通过后写） | 3.4 全局流程总结、3.3 页面说明 |
| 短信正文 | 3.3 页面说明-文案维度 | 3.3 页面说明-交互维度、5 验收标准 |
| 产品机制骨架 | 3.1 产品机制骨架 | 3.3 页面/组件明细、4 全局流程总结 |

## 五、自检方法

写完文档后，逐项检查：

1. **搜关键字**：把校验规则、Toast 文案、用户可见文案各搜一遍，看是否出现重复定义
2. **问自己**：如果这条规则要改，我需要改几个地方？如果超过 1 个，说明有重复
3. **看引用表**：引用关系是否覆盖了所有跨章节引用？是否有"被引用位置"写了完整内容而非引用指针？

## 六、效果

- 改一处即全局生效，消除漏改风险
- 文档冗余度降低约 40-50%，信息量不变
- 评审人能快速定位信息的权威来源
