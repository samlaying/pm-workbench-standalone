# Meeting Notes Organizer

处理会议材料，按项目归档，按类型生成对应产物。

## 触发条件

用户贴入会议内容（飞书妙记转写、会议笔记、口述回忆等），或说"记录一下""帮我拆""处理一下会议"等。

## 核心原则

先读 `../_shared/workflow-rules.md`，按公共规则完成项目识别、上下文获取和结构化确认。

1. **会议不是独立产物** — 每次会议都属于某个项目的上下文链路
2. **先读后处理** — 带着项目已有认知去理解新会议，而不是白纸状态提取信息
3. **增量而非重复** — 项目上下文中已有的信息不重复记录，只记变化和新增
4. **一次问完** — 前置确认一次性完成，不反复追问

---

## 流程

### 1. 前置准备

#### 1.1 识别项目

按公共规则判断项目和需求点归属。多项目材料先列出识别结果和证据，再让用户确认拆分处理还是指定主项目。

#### 1.2 读取上下文（必须，不可跳过）

按公共规则读取最小上下文；如果有活跃 MT 沟通，再扫描 `{项目目录}/需求点/` 下的 `00-对齐记录.md`。读取后在内部形成"已有认知清单"，用于后续处理时对比。

#### 1.3 快速扫描会议内容

识别：
- 涉及哪些需求点/功能模块
- 有哪些待办、决策、问题
- 与"已有认知清单"中的哪些条目相关
- 是否涉及对某项目**流程/系统/数据口径/技术选型**的讨论（命中则触发"技术细节提取"，见 3E）

---

### 2. 确认（一次性问完，共3~4个问题）

一次性向用户确认以下3~4个问题：

```
1. 文件名：{YYYYMMDD} {类型}-{对象}-{主题} → OK？（我建议的是：...）
2. 会议类型：需求评审 / MT沟通 / 周会 / 跨部门 / 日会？（我猜是"..."）
3. 处理模式：只记录 / 处理？
4. （仅当 1.3 命中技术/流程讨论）提取到「技术细节文档」？目标项目？（默认：{会议所属项目}；可指定到讨论实际所属的其他项目）
```

**AI 应尽量准确猜测会议类型和文件名，减少用户操作。**

默认处理模式建议：
- 需求评审 → 默认"处理"
- MT沟通 → 默认"处理"
- 周会 → 默认"只记录"
- 跨部门 → 默认"处理"
- 日会 → 默认"处理"

---

### 3. 按类型路由处理

用户确认后，按以下类型分别处理。

---

#### 3A. 需求评审

**产出：**
- 会议记录 → `会议纪要/{YYYYMMDD} 需求评审-{主题}.md`（使用 `meeting-record.md` 模板）
- 如"处理"模式 → 需求点文件夹 + `01-理解.md`（使用 `meeting-todo.md` 模板）

**查找或创建需求点：**
1. 扫描项目目录下 `需求点/` 文件夹，按名称匹配
2. 匹配到 → 读取已有 `01-理解.md`（如有），合并信息，不覆盖已有内容
3. 未匹配 → 建议创建 `需求点/需求点{NN}-{功能名}/`，等待用户确认编号和名称。创建时预制标准文件：`01-理解.md`、`10-过程记录.md`、`100-成品.md`、`500-复盘.md`

**01-理解.md 处理规则：**
1. 使用 `meeting-todo.md` 模板
2. 执行上下文增强（见下方"上下文增强规则"）
3. 理解和关键信息写入 `01-理解.md`
4. 行动项写入 `10-过程记录.md` 的"行动项"段落
5. 双链关联到本次会议记录

---

#### 3B. MT沟通

**产出：**
- 会议记录 → `会议纪要/{YYYYMMDD} MT沟通-{主题}.md`（使用 `meeting-record.md` 模板）
- 如"处理"模式 → 需求点文件夹 + `00-对齐记录.md`（使用 `mt-alignment.md` 模板）

**查找或创建需求点：**
同需求评审。

**00-对齐记录.md 处理规则：**

1. 使用 `mt-alignment.md` 模板
2. **查找已有对齐记录**：
   - 扫描需求点文件夹下是否已有 `00-对齐记录.md`
   - **有** → 读取完整内容，将新轮次插入到"当前状态"分隔线之后、历史轮次之前
   - **没有** → 创建新文件，这是第1轮
3. **时间间隔检查**：
   - 读取上一轮次的日期
   - 计算间隔天数
   - 间隔 > 7天 → 在输出开头加提醒块：
     ```
     > ⏳ 距上次沟通已过 {N} 天。上次结论：{摘要}。以下基于这个前提继续，如有变化请告诉我。
     ```
   - 间隔 ≤ 7天 → 正常追加
   - 第一轮 → 不提醒
4. **上下文增强**（见下方规则），重点标注"和上轮相比变了什么"
5. **自动更新"当前状态"**：每次追加后，用最新结论覆盖"当前状态"区域
6. **行动项同步**：
   - 行动项统一写入 `10-过程记录.md` 的"行动项"段落
   - 如需求点下没有 `10-过程记录.md` → 创建

---

#### 3C. 周会

**产出：**
- 会议记录 → `会议纪要/{YYYYMMDD} 周会.md`（使用 `meeting-record.md` 模板，填写周会扩展段）
- 如"处理"模式 → 更新 `项目上下文.md`

**处理规则：**
1. 使用 `meeting-record.md` 模板，填写"周会进展"扩展段
2. 进展表格中对比项目上下文中各需求点的当前状态，**只记变化**
3. 风险/阻塞与项目上下文中的已有风险对比，标注 `[新增]` 或 `[持续]`
4. 回写项目上下文：
   - 在会议记录末尾的"回写项目上下文"段列出要更新的内容
   - AI 直接更新 `项目上下文.md` 对应章节，不覆盖已有内容，只追加/更新状态字段

---

#### 3D. 跨部门上线 / 日会

**自动判断规模：**

- 内容显示单次对齐（"拉通上线排期""确认各方时间"）→ **小场景**
- 内容显示持续跟踪（"昨天做了什么""今天阻塞"）→ **大场景**
- 不确定 → 问用户

**小场景：**

产出：
- 会议记录 → `会议纪要/{YYYYMMDD} 跨部门-{主题}.md`
- 如"处理"模式 → `需求点/需求点{NN}-{功能名}/01b-上线对齐.md`（使用 `cross-team-alignment.md` 模板）

**大场景：**

产出：
- 每日记录 → `会议纪要/{YYYYMMDD} 日会-{主题}.md`（使用 `daily-streak.md` 模板）
- 如"处理"模式 → 更新 `需求点/需求点{NN}-{功能名}/01b-上线对齐.md`（总看板）

**日会处理规则：**
1. 只记增量：昨天→今天的变化、今日阻塞、今日行动项
2. 不重复已有信息
3. 每条日会记录双链到 `01b-上线对齐.md`
4. `01b-上线对齐.md` 作为总进度看板持续更新各节点状态

**查找或创建 01b-上线对齐.md：**
- 需求点下已有 → 读取，更新节点状态
- 没有 → 创建

---

#### 3E. 技术细节提取与维护（跨类型，命中即执行）

当 1.3 扫描命中"技术/流程讨论"**且**用户在确认环节（第 4 问）同意提取时，**与类型路由（3A–3D）并行**执行本节。

**目标项目**：确认环节第 4 问指定的项目（默认 = 会议所属项目；可指定到讨论实际所属的其他项目——会议归档在 A，讨论的技术细节可能属于 B）。

**查找或创建**：
- 读取 `{目标项目}/技术细节.md`
- **有** → 在现有基础上增量更新（见下），切勿整体覆盖
- **没有** → 用 `tech-details.md` 模板创建；**首次创建时**从 `{目标项目}/项目上下文.md`（需求点清单/关键背景）+ `{目标项目}/内部术语表.md` 预填已知流程，作为现状表骨架

**现状表维护**：
1. 本次会议**讨论到的**流程：填/更新技术细节，对比旧值用上下文增强标注（`[新]/[变化]/[延续]`）；`[变化]` 必须附来源会议双链，写明"之前是 X → 现在是 Y"
2. **未讨论到的**流程：保持原状或留空（"— 未提及 —"），不要臆测
3. 新讨论到、表里没有的流程 → 末尾加行
4. 更新对应行的"最后更新"与"来源会议"

**决策记录表维护（按类型分流）**：
- **技术/流程决策**（哪个系统处理哪个流程、数据口径、接口对接、技术选型）→ 追加一行到本表，双链回本次会议
- **项目/产品决策**（范围、优先级、业务规则、go/no-go）→ 走既有"回写项目上下文"机制，进 `项目上下文.md` 的「关键决策记录」，**不**写进本表
- 决策记录表只追加，不修改历史行；同一决策后来变了就加新行

**双链与行动项**：技术细节文档 ↔ 本次会议记录、相关需求点互相 `[[wikilink]]`。行动项仍写 `10-过程记录.md` + `任务.md`，不在本文件记。

---

### 4. 后处理

每次处理完成后，检查以下事项：

1. **原始文件处理**：
   - 将原始文件重命名为规范文件名（如 `1.md` → `20260528 跨部门-埋点沟通.md`），**不删除**
   - 如果原始文件已经按规范命名，则直接在原文件基础上补充上下文增强标注
2. **回写清单**：如果会议记录或需求点文件中有"回写项目上下文"的条目，执行回写
3. **双链完整性**：
   - 会议记录中有到需求点的链接
   - 需求点的对齐记录/理解文件中有到会议记录的链接
   - 会议记录中引用其他会议时使用 `[[wikilink]]`
   - 会议记录的"相关会议"段列出所有被引用的会议
4. **对齐记录一致性**（MT沟通专属）：`00-对齐记录.md` 的"当前状态"区域是否已更新为最新结论
5. **技术细节双向链接**（执行了 3E 时）：`技术细节.md` 与本次会议记录、相关需求点是否互相 `[[wikilink]]`；决策记录表是否只追加了技术/流程类决策（项目/产品决策应去项目上下文）

---

### 5. 写入项目任务文件

如本次处理产出了行动项（无论哪种会议类型），将行动项同步写入 `{项目目录}/任务.md`：

1. 读取已有 `任务.md`（如存在），否则创建
2. 检查是否有重复任务（通过描述关键词匹配），避免重复添加
3. 在文件顶部（frontmatter 之后）追加新段落：
   ```
   ## [[本次会议记录文件名]] — {YYYY-MM-DD}

   - [ ] {行动描述} 📅 {截止日期} {优先级} @{负责人}
   ```
4. `任务.md` 是汇总视图，行动项的"源头"在 `10-过程记录.md`，两边格式保持一致
5. 截止日期推断：
   - 会议中明确说了时间 → 用那个时间
   - 行动项标注了 P0 → 📅 +2天
   - 行动项标注了 P1 → 📅 +5天
   - 行动项标注了 P2 → 📅 +10天
   - 无法判断 → 不加日期
6. 优先级映射：P0 → `🔼`，P2 → `🔻`，P1 → 不加
7. 如该行动项在之前的会议中已经写入过 `任务.md`，且本次会议有新进展（状态变化、截止日期调整），更新已有条目而非重复追加

## 文件命名规范

| 类型 | 命名 | 示例 |
|---|---|---|
| 会议记录 | `YYYYMMDD {类型}-{对象}-{主题}.md` | `20260528 跨部门-mkt-产品发布情况介绍.md` |
| 需求点文件夹 | `需求点/需求点{NN}-{功能名}/` | `需求点/需求点01-搜索优化/` |

会议类型关键词：需求评审、MT沟通、周会、跨部门、日会

**对象**：和谁开会（对方团队/人名），如 mkt、研发、张三、李四 等。

需求点编号按创建顺序递增，不跳号。

## 双链规范

使用 Obsidian `[[wikilink]]` 语法：

### Frontmatter 链接

- 会议记录 frontmatter 中：`关联: [[需求点01-搜索优化]]`
- 对齐记录轮次中：`会议: [[20260528 MT沟通-搜索优化]]`
- 理解文件 frontmatter 中：`会议: [[20260528 需求评审-搜索优化]]`
- 日会记录中：`看板: [[需求点01-搜索优化/01b-上线对齐]]`

### 正文双链

- 上下文标注引用其他会议时，必须用 `[[wikilink]]` 而非纯文本：`[变化]` 之前结论是"当前模型够用"（见 [[20260520 MT沟通-搜索]] ）
- 会议记录末尾的"相关会议"段列出所有被引用的会议，确保 Obsidian Graph 中可见

## 上下文增强规则

这是区别"简单重组原始材料"和"真正有帮助"的关键。每次处理会议内容时，必须将提取的信息与前置准备中读取的"已有认知清单"对比，在对应信息旁边直接标注。

### 标注类型

| 标注 | 含义 | 使用场景 |
|---|---|---|
| `[延续]` | 与已有认知一致 | 会议中再次确认了已知结论 |
| `[新]` | 之前没有这条信息 | 全新的信息点 |
| `[变化]` | 与之前认知不同 | 方向调整、结论修改、优先级变更 |
| `[冲突]` | 与项目上下文中的历史决策矛盾 | 需要特别关注，可能需要回溯 |
| `[新增]` | 新增的风险/依赖 | 风险章节使用 |
| `[持续]` | 已知风险，仍在 | 风险章节使用 |
| `[已解除]` | 之前的风险已解决 | 风险章节使用 |
| `[学习机会]` | 某人提到了你不熟悉的领域/做法 | 标记可以找谁快速建认知地图 |
| `[求助线索]` | 某人可能能帮解决当前卡点 | 标记后续可以找谁求助 |

### 标注位置

**在对应信息旁边直接标注，不要集中写在一个段落。**

示例：
```markdown
- 搜索质量需要重新评估模型 → `[变化]` 之前结论是"当前模型够用"（见 [[20260520 MT沟通-搜索]] ）
- 新增风险：YY团队排期不确定 → `[新增]` 项目上下文中未提及
- 确认沿用V2方案 → `[延续]` 与 [[20260515 需求评审-搜索]] 结论一致
```

### 上下文引用

如果标注了 `[变化]` 或 `[冲突]`，必须附上引用来源（哪次会议、什么结论），用双链指向相关会议记录。

如果待确认问题与项目上下文中已有信息相关，在"已知背景"字段中附上已有信息，避免重复提问。
