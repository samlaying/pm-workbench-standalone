# 汇报/通知文档写作 Skill

## 触发条件

- 用户说"帮我写个汇报""写个通知""整理一下发出去""同步一下进展""写个文档上传飞书"。
- 用户给了一段事情描述，要求整理成正式文档。

## 不触发

- 需要写 PRD / 需求文档 → 改用 `prd-writer`。
- 只整理会议纪要、拆任务 → 改用 `meeting-notes-organizer` / `task-arrangement-planner`。
- 只维护项目背景、术语 → 改用 `project-context-maintainer`。
- 评审后处理反馈、写验收标准 → 改用 `prd-review-handler`。

## 核心原则

先读 `../_shared/workflow-rules.md`，按公共规则完成项目识别、上下文获取和结构化确认。

### 写作原则

1. **金字塔原理**：结论先行，以上统下，归类分组，逻辑递进。读者看完第一句就知道这篇文档要说什么。
2. **摘要优先**：长文档（超过 3 个一级章节）必须在顶部放摘要，3-5 句话概括：发生了什么、影响什么、需要谁做什么。
3. **大纲可见**：每个一级章节开头用一句话说明本章结论，让读者不用通读也能抓住重点。
4. **不写八股文**：不要"尊敬的领导""特此汇报""综上所述"等套话。用直接、清晰的语言。
5. **零错别字**：格式混乱、错别字会让读者质疑内容质量。
6. **面向行动**：通知类文档必须回答"读完之后，我需要做什么"。汇报类文档必须回答"这件事的结论和下一步是什么"。

### 形式要求

- 一级大纲不超过 5 个，每个一级下不超过 4 个二级。
- 每段不超过 5 行；超过就拆或提炼。
- 关键数字、结论、待办用高亮或加粗。
- 表格优于长段文字（用于对比、状态、分工）。
- 文档超过 1 页时，顶部放摘要块。

### 汇报 vs 通知的侧重

| 维度 | 汇报（给领导/上级） | 通知（给协作方/团队） |
|------|---------------------|---------------------|
| 核心 | 结论 + 风险 + 需要的支持 | 发生了什么 + 对你的影响 + 你需要做什么 |
| 语气 | 简洁、直接、不回避问题 | 清晰、不啰嗦、尊重对方时间 |
| 行动 | 明确"需要您决策/支持什么" | 明确"请在什么时间前做什么" |
| 长度 | 能短则短，补充材料放附件 | 能短则短，关键信息不遗漏 |

## 流程

### Phase 0：读取上下文

按公共规则确认项目并读取最小上下文。带着这些认知进入 Phase 1，不向用户复述完整上下文。

### Phase 1：澄清确认

基于用户给的初始描述 + 读到的项目上下文，一次性结构化确认以下信息：

1. **受众**：这份文档给谁看？（领导 / 跨团队 / 项目组 / 全公司？）
2. **目的**：核心目的是什么？（汇报进展 / 通报风险 / 通知上线 / 请求支持 / 同步决策？）
3. **范围**：涵盖哪些内容？（AI 基于初始描述 + 上下文给出建议范围，用户确认或修改）
4. **上传飞书**：是否需要上传飞书？目标文件夹？（默认：是）

每个问题给 2-4 个选项 + Other。选项基于上下文尽量准确猜测，减少用户操作。

### Phase 2：生成文档

#### 2.1 确定文档结构

根据受众 × 目的，选择合适的结构：

**汇报类（给领导/上级）：**
```
摘要（3-5句）
├── 结论 / 核心信息
├── 背景（极简，只说必要的上下文）
├── 详情（按逻辑分组，每组先说结论）
├── 风险 / 阻塞（如有）
└── 需要的支持 / 下一步
```

**通知类（给协作方/团队）：**
```
摘要（3-5句）
├── 发生了什么
├── 对你的影响
├── 你需要做什么（含时间节点）
└── 补充信息（如有）
```

**进展同步类：**
```
摘要（3-5句）
├── 上次同步以来的变化
├── 当前状态（表格）
├── 风险 / 阻塞
└── 下一步计划
```

#### 2.2 写作要求

1. 结论先行：每个章节的第一句话就是该章的结论。
2. 用项目上下文中的术语，不自造词。
3. 关键数据、时间、人名加粗。
4. 待办项明确到人 + 时间。
5. 风险项写明影响范围和缓解措施。
6. 不写与目的无关的内容。

#### 2.3 本地落盘

文档保存到：
- 如属于某个项目 → `{项目目录}/会议纪要/{YYYYMMDD} 汇报-{主题}.md` 或 `{项目目录}/需求点/需求点{NN}-{功能名}/100-成品.md`
- 如不属于特定项目 → `00-Inbox/{YYYYMMDD} 汇报-{主题}.md`

文件名用结构化确认。

### Phase 3：上传飞书

1. 用结构化确认来确认：上传文件、目标文件夹、同名文档处理方式。
2. 读取 `lark-docx-formatting.md`（在 `../prd-writer/` 下）。
3. 将 Markdown 转成飞书 DocxXML。
4. 创建或更新飞书文档。
5. 返回飞书链接。

暂停点：用结构化确认来检查飞书文档可打开、格式正常。

---

## 输出约束

- 最终文档必须是可直接发给受众阅读的成品，不是草稿。
- 文档本地保存为 Markdown，飞书上传为 DocxXML。
- 上传后在 `项目工作记录.md` 追加记录（如属于项目）。
