# 任务安排规划 Skill

## 前置要求

先读 `../_shared/workflow-rules.md`，按公共规则完成项目识别、上下文获取和结构化确认。

用户至少提供：
- 项目名
- 领导/相关人安排的原话或任务描述

若缺失，先问 1-2 个问题补齐。

## 核心理念

> **"这事不难，这事只是很复杂。"**

绝大多数让人觉得"不可能完成"的工作，不是因为真的"难"，而是因为"碎"——目标碎、关系碎、步骤碎。你不是能力不够，而是被复杂度吓住了。

- **难** → 需要超凡天赋或极限努力
- **复杂** → 线头多、环节多、相关方多，但可以拆解、可以一步步做

本 skill 的目标：**先看清、再拆开、找对人、然后边做边调。**

---

## 复杂度判定

拿到任务后，先快速判断复杂度，决定走哪条流程：

| 维度 | 简单 | 复杂 |
|------|------|------|
| 相关方 | 1-2 个，关系清晰 | 3+ 个，或涉及跨部门/多方利益 |
| 目标 | 明确，一句话说得清 | 模糊，或有多个互相牵扯的子目标 |
| 执行路径 | 做过类似的事，路径已知 | 没做过，或路径不确定 |
| 资源 | 手头基本够用 | 缺人/缺信息/缺权限，需要调动 |

**2 个及以上维度命中"复杂"→ 走完整五步流程。**
**否则 → 走轻量流程。**

---

## 轻量流程（简单任务）

和原有流程一致，快速出结果：

1. 按公共规则读取上下文；需要沉淀长期记忆时，复用 `project-context-maintainer` 的更新规则。
2. 判断这是独立任务，还是大项目下的小需求点。
3. 提取任务画像：
   - 谁安排的
   - 要解决什么问题
   - 期望交付物
   - 截止时间/同步节点
   - 相关人
   - 已知约束
   - 不清楚但会影响推进的问题
4. 给出"还需要用户提供什么信息"清单，只列真正影响推进的信息。
5. 给出工作节奏：
   - 今天/下一步先做什么
   - 要找谁确认什么
   - 先产出哪个低成本版本
   - 什么时候同步
   - 哪些风险需要提前暴露
6. 如用户要落盘，写入：
   - 独立项目：`{项目目录}/任务安排/{YYYY-MM-DD}-{任务名}.md`
   - 小需求点：`{项目目录}/需求点/{需求点名称}/任务安排/{YYYY-MM-DD}-{任务名}.md`
   - **同时将"下一步行动"中的可执行项写入 `{项目目录}/任务.md`**（格式见下方任务格式规范）
7. 回写项目上下文和项目工作记录。

## 完整五步流程（复杂任务）

### Step 1：外部视角 — 搞清"真目标"

复杂工作的第一个陷阱是**目标迷失**。线头多、领导多、要求多，容易陷入"什么都重要"的混乱。

**跳出执行者身份，像局外人一样问：**

1. 这件事到底要解决什么问题？（不是"要做什么"，是"要解决什么"）
2. 如果目标是这个，当前方案是最好的吗？
3. 不做这件事，最坏会怎样？（判断真实优先级）

**输出：**
- 一句话定义真目标（不超过 25 个字）
- 当前方案的替代选项（如有）
- 目标的置信度：高/中/低

> 如果置信度是"低"，不要急着往下走——先花 30 分钟把目标搞清楚，比后面返工节省 10 倍时间。

---

### Step 2：拆解目标 — 化整为零

看清了真目标之后，复杂性仍然存在。把复杂拆成不复杂的单元。

#### 2.1 利益相关方拆解

事的复杂往往本质是"人的复杂"。把所有相关人分类：

| 角色 | 谁 | 怎么对待 |
|------|-----|---------|
| 盟友 | | 争取支持，提前通气 |
| 障碍 | | 了解顾虑，找到绕过或化解的方式 |
| 合作对象 | | 明确分工，建立定期同步 |
| 争取对象 | | 用对方听得懂的语言讲价值 |
| 受益者 | | 让他们知道"这事对你有什么好处" |
| 资源方 | | 说明需要什么、什么时候要 |

**关键技巧：把所有人都变成"自己人"** — 会前一对一沟通，让每个人的意见都体现在方案里，这样支持你就是支持他自己的投入。

#### 2.2 动作组合

把步骤写出来。脑子里的模糊想法必须被结构化才能被执行。

按时间顺序列出所有需要做的事，标注：
- 这一步的产出是什么
- 这一步依赖什么前置条件
- 这一步谁来做

#### 2.3 资源盘点

| 需要什么 | 手头有什么 | 缺口 | 怎么补 |
|----------|-----------|------|--------|
| | | | |

目标、动作、资源三者需要动态匹配——缺资源就调整动作，或降低目标。

---

### Step 3：框架性学习 — 快速建认知地图

你没干过这件事，不代表你要在黑暗中摸索。先建一个粗略的地图。

**在动手前，花 1-2 小时做这些事：**

1. **搜**：这件事的行业惯例、竞品做法、内部历史经验
2. **读**：相关文档、历史 PRD、之前的项目上下文（`project-context-maintainer` 可以帮你快速拉取）
3. **找人**：找到这个领域的人聊 15-20 分钟

> 找人不怕找错——每个"错的人"都是你找到"对的人"的路标。

**输出：**
- 我对这件事的认知盲区在哪
- 有哪些已有的经验/资料可以直接复用
- 下一步行动的调整（基于新认知）

---

### Step 4：求助 — 打开局面

**第一个执行动作不是"做"，而是"问"。**

你面对的复杂问题，对别人可能只是举手之劳。

求助的三重价值：
1. **降低执行成本** — 别人的经验可以直接帮你跳过弯路
2. **倒逼你澄清目标** — 你必须跟别人讲清楚你在做什么、有什么价值，否则别人不会帮你
3. **建立关系网络** — 每一次求助都是一次连接

**求助清单：**

| 我需要什么 | 找谁 | 怎么开口 | 优先级 |
|-----------|------|---------|--------|
| | | | |

**话术模板：**

> 我在做【一句话说清楚事情】，目标是【解决什么问题】。你在【某个领域】比我有经验，想请教【具体问题】。大概占用你【时间】，方便吗？

---

### Step 5：迭代计划 — 少想多做

不存在静态的最优方案，所有好结果都是"做"出来的。

**不要一次性排出全部计划。** 改为：

1. **本周计划**：明确本周要完成的 2-3 件事
2. **第一个里程碑**：做到什么程度先同步一次（不要等到"完美"再同步）
3. **迭代节奏**：每【N天】做一次小同步，根据反馈调整

> 你的每个行动都会改变事情本身的形态，所以根本不存在一个事先算好的完美方案。正确的方式是：做 → 观察变化 → 调整 → 再做。

**输出：**
- 本周具体行动计划
- 第一个同步节点（什么时候、跟谁、同步什么）
- 需要提前暴露的风险

---

## 写入 任务.md 规则

1. 读取已有 `{项目目录}/任务.md`（如存在），否则创建
2. 检查是否有重复任务（通过描述关键词匹配），避免重复添加
3. 在文件中追加新段落，按来源分组：
   ```
   ## 任务安排 — {YYYY-MM-DD} {任务名}

   - [ ] {行动描述} 📅 {截止日期} {优先级} @{负责人}
   ```
4. 截止日期推断：P0 → 📅 +2天，P1 → 📅 +5天，P2 → 📅 +10天，无法判断则不加
5. 优先级映射：P0 → `🔼`，P2 → `🔻`，P1 → 不加

## 判断原则

- 先帮用户降低不确定性，再安排执行。
- 不追问所有缺口，只追问会影响方向、范围、截止时间、交付物的问题。
- 给用户可直接发送给领导/同事的话术。
- 把"待确认"和"建议先按此推进"分开。
- **复杂任务不要一次排完所有计划**——先排本周，设好同步节点，在行动中迭代。

## 输出格式

- 简单任务：使用 `templates/task-arrangement.md`
- 复杂任务：使用 `templates/task-arrangement-complex.md`

| 类型 | 文件 | 说明 |

| 模板 | `templates/task-arrangement.md` | 轻量任务安排模板 |
| 模板 | `templates/task-arrangement-complex.md` | 复杂任务五步框架模板 |
